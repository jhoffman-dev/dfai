Connect other tools

DFAI has a local API and an MCP server, so Claude Code, Claude Desktop and scripts can search, read and write your vault while DFAI is open.

  1. Settings (⌘,) → Connections → turn on Local API. It's off until you do.
  2. Build the MCP server once: pnpm --filter @dfai/mcp build
  3. Press Copy MCP command and run it in a terminal, or use this:
claude mcp add atlas -- node ~/Projects/atlas/apps/mcp/dist/main.js

Then ask Claude things like “find my open tasks in phase 17” or “make a task to call Sam”. It reads a note before changing it, and never overwrites unsaved typing. Nothing can be deleted through the API, and the only things it moves are a note into or out of the Archive, and a note out of the Inbox to its home folder when it's filed. A new note with no folder (POST /v1/notes) goes in its type's home. Rotate token in Settings cuts off anything using the old key.

What Claude can do besides reading and writing notes

  • Add a picture to a note (atlas_add_image). From a file, it reads only PNG, JPEG, GIF, WebP, SVG or HEIC images up to 20 MB in your Desktop, Downloads or Pictures folder, or the temporary folder — never anything else on the disk. To use other folders, set ATLAS_MCP_IMAGE_DIRS to them, separated by :; it replaces the list. The picture lands where pictures you add do, and a link to it goes at the end of the note.
  • Open today's note (atlas_daily_note, POST /v1/daily): found, or made exactly as ⇧⌘D makes it. Capture a task (atlas_capture_task, POST /v1/capture) into the Inbox, as quick capture does. The global shortcut itself is a key on one Mac, set in Settings; it isn't reachable through the API.
  • Quick add a note of a type (atlas_quick_add, POST /v1/quick-add): a name and a few fields, from the type's template, in its home folder. atlas_quick_add_types (GET /v1/quick-add) lists the types it offers and what each asks for. Choose them in Settings (⌘,) → Quick add — The types Claude and your other tools can quick-add through DFAI’s local API and MCP: Add a type… adds one (five at most), drag to reorder, and the × beside one removes it.
  • Read each task's schedule (atlas_query with schedule): its estimate, the time its blocks set aside, what is done and how far it is over — the same numbers as the task's page. Blocks are notes, made and changed like any other.
  • Schedule a task (atlas_schedule_task): a new block for it from a start, for some minutes, linking it — or, with no minutes, as long as it still needs — the same as dragging it onto the calendar's empty time. Ask again to split it across another block.
  • See whether Google Calendar is connected (atlas_status, GET /v1/status): googleCalendar: { connected }, and nothing more. Claude can't read or change your Google calendar or see the sign-in; connecting stays in Settings.
  • Read a day's meetings (atlas_day_meetings, GET /v1/calendar/meetings?day=YYYY-MM-DD): the meetings from Google Calendar on that day, as Today lists them, earliest first, with their people, companies and meeting note. Declined, cancelled and all-day events are left out. It reads the notes in the vault, never Google.
  • Read a calendar view's days (atlas_calendar): which notes fall on which day of a saved view's calendar, and which have no date yet.
  • Refresh a source (atlas_refresh_source), as its Refresh button does — at most once every 30 seconds per source, and only where the source may run.
  • List tags and their notes (atlas_tags, atlas_tagged_notes), as the Tags page does. A tag used only in templates isn't listed.
  • Read how names are spelt (atlas_terms): every term, every spelling DFAI puts right with what it should be — terms' misheard spellings, and people's and companies' names as right spellings with their misheard spellings (their aliases are left out) — and the conflicts, which Claude is told never to correct. Read-only: Claude adds a term by making a note with type: term, and changes its misheard spellings as it changes any property. A person's or company's misheard spellings go in that note's own variants, not in a term.
  • Archive and unarchive (atlas_archive, atlas_unarchive), up to 100 notes at a time, by the same rules as the app, updating links as it goes. A note with unsaved typing in DFAI is left where it is and reported, since Claude never saves your typing for you. atlas_archived lists and searches the Archive.
  • Clarify an Inbox task (atlas_clarify_inbox_item): give one waiting item its status, who it waits on, defer, due, contexts and project in one save, by the same rules as its row on the Inbox page — Waiting never needs a person, and a refusal writes nothing. atlas_inbox lists what waits, each task with what it already says, 500 at a time with how many wait in all — it reads on past the first 500 as the page's Show more does, from where the last page ended, so Claude can file what one page listed before asking for the next and miss nothing.
  • Process the Inbox (atlas_process_inbox_item): file a waiting note under a project or an area, by the same rules as the Inbox page — linked, out of the Inbox folder to its home folder, links to it updated. Anything that isn't a project or an area still in use is refused before the note moves, and a note with unsaved typing in DFAI is left where it is. atlas_capture_task captures into the Inbox, starting a GTD task at Inbox; atlas_update_properties is held to the same task rules as the app — Archive writes the day, and Waiting never needs someone — and moving a vault's tasks to GTD stays in the app. atlas_inbox lists what's waiting to be filed, as the Inbox page does — each meeting with what the import made of it, and no proposals, which Claude answers with the proposal tools and can't file.
  • Answer proposals (atlas_proposals, atlas_accept_proposal, atlas_reject_proposal): list what is waiting in the Inbox and accept or reject one, by the same rules as its buttons — nothing written over, a proposal with unsaved typing left alone. Ask Claude to show you a proposal before it accepts; editing one first and Undo stay in the app.
  • Make a checklist line a task (atlas_promote_checklist_line), as Make task does: name the line by its words or its markdown, and by its place only if two say the same; a line that is a task already is refused. There is no undo from Claude — that sends a note to the Trash, which stays in the app. A note's progress comes back in the rows of atlas_query and atlas_run_view, and as progress in atlas_run_query.
  • Run a saved query view (atlas_run_view), the same as any view: it answers with the query's rows as the app finds them — the query's own INCLUDE ARCHIVED decides whether archived notes come too — and a query with a mistake is refused with the reason. A grouped table or board view answers its groups and sub-groups beside its rows, in the order the app draws them — a board every column, an empty one too, since that's somewhere to move a card; a gallery only its first level. atlas_list_views shows each view's Group by and Then by, and its place among its type's tabs; it lists Today and Inbox first, as the sidebar lifts them — they're views too, run by their paths like any other — then the other views by name, then the dashboards. Changing a view's grouping stays in the app.
  • List a type's views (atlas_list_type_views), in the same tab order the app shows, with each view's name and layout. A type with no views answers its default table, which isn't a file yet, so run it with a query (atlas_run_query with FROM the type) instead. Up to 500 at a time. Adding, renaming, copying, reordering and deleting views stay in the app.
  • Move a card on a board (atlas_move_card) to another column, another lane, or both, by the same rules as dragging it: one write, and a task finishes only through its type's status, a repeating one rolling on to its next date once. Only the board's own columns and lanes are accepted; anything else is refused, naming them, so Done for done never makes a column the type doesn't have. A move that would finish a task needs the note's last-modified time, so a retried move can't finish a repeating task twice. Only a board's cards move — a view note can't be moved this way.
  • Add a note in a group (atlas_add_to_view), as + New in that group does: it gets the group's value, and the sub-group's, typed as the property stores them, and is numbered past any note of the same name. Only .md notes are made.
  • Run a query you'd build (atlas_run_query): the same queries as the builder or the text, read-only. It answers with the rows, and with the groups and sub-groups for GROUP BY, as the app groups them. Give it a note as context and this in the query means that note — “Mara Quill's meetings in the last 30 days” is FROM meeting WHERE people = this AND date > @-30d AND date <= @today with her note as context; a note that isn't there is refused. To answer a query block a note holds, send the query after its layout: line with that note as context. A mistake comes back with its line and column. Archived notes come only when the query's text says INCLUDE ARCHIVED. Up to 5000 rows. Notes in .atlas or a hidden folder are never reached, not even through a relation. Saving a query as a view stays in the app.
  • Read today (atlas_today): the same sections as the Today page — overdue, due today, back from deferral, in progress, next actions by project, waiting by person with its days — plus the Inbox's count and the stalled projects, read on the app's clock, writing nothing. It starts with what's chosen for today and what's carried over, and says whether the vault chooses for today at all. To act on a task, Claude sets its status or Defer until with atlas_update_properties.
  • Choose for today (atlas_choose_for_today, POST /v1/today/choose): chooses a task for today, or takes it off, the same as the Today page's Today, Keep and Drop. It uses the app's day, and writes the note as the page does. It's refused, writing nothing, where the vault doesn't choose, or where the task's focus is your own.
  • Tick a task done (atlas_tick_task, POST /v1/tasks/done): what a task's box does on Today and in a GTD view — finished with today's date, or a repeating task rolled on to its next day, and a choice for today ended. A task that is finished already is left as it is. Unticked, a finished task goes back to Next Action. It needs the task's modified as Claude read it, so a tick sent twice never rolls a task on twice. To set any other status, Claude changes the property.
  • Take the weekly review (atlas_weekly_review): the same sections as the Weekly review page, read on the app's clock, writing nothing. To act on an item, Claude sets its status or Defer until with atlas_update_properties, or archives a project with atlas_archive. One difference from the page: Claude setting a repeating task to Archive ends its series, where the page's Archive rolls it on.
  • Read automations (atlas_automations, atlas_automation_log, atlas_automation_dry_run): every rule with its schedule or the note that sets it off, last run, next run and why it's paused, rules whose file can't be read listed apart; a rule's log, newest first, up to 100 entries; and exactly what a run would do now, writing nothing — up to 500 notes, with how many more it would pass over; for a rule that asks Claude, the prompt or skill and the tools it would use, without asking Claude. Running, undoing, and making or editing a rule stay in the app.
  • List meetings (atlas_meetings), newest first, read-only: each one's date, start, provider and id, with importOutcome (imported, duplicate, error; pending while a file waits for the Mac that imports; empty for a meeting elsewhere DFAI never imported), importError saying why a file that arrived could not be imported, and duplicateOf naming the meeting a second copy duplicates. since keeps those on or after a day; second copies are archived, so they're listed only with includeArchived. Ask Claude “which meetings came in this week, and did any fail?” To fix a failed one, Claude edits the file as any note, and DFAI imports it once it reads.
  • Receive a meeting (POST /v1/meetings): how n8n sends a meeting in — see Meetings. DFAI writes it into its month, Meetings/2026/10/, once per provider and id: 201 when it's written, 200 when the vault already has it. There's no MCP tool for it; Claude records a meeting by making a note.
  • Capture a Slack message (atlas_capture, POST /v1/captures): how a Slack message comes in, under the capture/v1 contract — see Capture from Slack. Once per message: 201 when it's written, 200 when the vault already has it, and a refusal that names every problem. Claude saves a message it read in Slack with atlas_capture, always with its Slack link — see three ways to save from Slack.
  • See archived notes: search, running a view and SQL queries leave them out, as the app does, unless asked with includeArchived.
  • Read your name (atlas_profile): the full name and preferred name from Settings → Profile, and [Your name] to write when there's no full name. Claude is told to use exactly that name for an owner, author, assignee or attendee, and never to guess one from a username, an email address or a path. Read-only: the name is changed only in Settings. If the settings can't be read, it says so rather than answer “no name”.
  • List and read templates (atlas_list_templates, atlas_read_template): every template with what it's used for — new notes of a type, today's note, captured tasks or saved artifacts — and which types have none, so their new notes start empty; and one template's properties and text, exactly what a new note made from it would start as. A template's name can be passed when making a note. Making, editing, renaming, deleting and moving templates to notes stay in the app.
  • List and read skills (atlas_list_skills, atlas_read_skill, GET /v1/skills, GET /v1/skills/{name}): every skill with its description and what is wrong with it, and one skill's instructions. Read-only: making, editing and deleting skills stay in the app.
  • Rename or merge a tag (atlas_rename_tag), by the same rules as the Tags page. It only previews unless told dryRun: false, and merges into a tag in use only when told to. Renaming to the same name in other capitals makes every spelling match. A rename that timed out may still finish, so preview again before retrying.
  • Export a note as Markdown (atlas_export_note, GET /v1/notes/{path}/export?format=markdown|standalone|confluence), read-only: markdown is the file as it is, standalone the Markdown that reads in any tool, as Export… writes it, and confluence a page for Confluence — see Share a note on Confluence below. The answer is the Markdown itself; nothing is written. A PDF or a Google Doc is made only in the app, since the API never writes outside the vault.

Share a note on Confluence

Ask Claude something like “put my Weekly sync note on Confluence, in the Team space”. Claude asks DFAI for the note as a page (atlas_export_note), then creates the page itself with its Atlassian connector, so that connector has to be connected in Claude too. DFAI never talks to Confluence and writes nothing — not to the note, not anywhere.

  • The page's title is the note's title, as its page in DFAI shows it.
  • A link becomes its words: its alias if it has one, otherwise the title of the note it names — [[mara quill]] reads Mara Quill, and a link to a heading reads Summer plans › Packing. A link to a block reads as its note's title, so a citation to a meeting line names the meeting.
  • An embed of a block or a heading (Blocks and embeds) is that block or section, quoted, under From Summer plans. One whose note or block is gone reads [Not found: …].
  • A callout becomes a quote that opens with its name in bold — Warning: Mind the gap.
  • Tasks, tables, code, headings and links and pictures on the web come across as they are.

Some things can't go on the page, and DFAI lists every one of them — Claude is told to tell you what was left out:

  • the note's properties (frontmatter);
  • where each link went — its words stay, but the page can't open a note in your vault;
  • pictures in your vault, which read [Image: …] — attach them to the page yourself;
  • files shown in place, like ![[diagram.png]], which read as their name;
  • block ids (^abc123), comments (<!-- … -->) — one you never closed hides the rest of its block, on the page as in the note — and whether a callout was folded.

A footnote in an embed is renamed after the note it came from, like [^Sources-1], so it can never be mistaken for one of this note's own.

Some blocks — one with a footnote, raw HTML or a comment in it — are tidied as written. DFAI then reads the tidied block again, and if it would come out differently on the page (HTML turned into a paragraph, say) or still points into your vault, that block goes across as plain words instead, and is listed under formatting by its first line, so you know which to fix up by hand.

Only notes outside .atlas and hidden folders are read for a title or an embed, so nothing from DFAI's own settings ever reaches the page.

Claude inside DFAI needs none of this. The chat pane (⇧⌘J) and Ask (⌘J) uses the same read tools in the app itself, with the Local API off, and proposes changes for you to accept rather than writing them.
Don't see the new tools? Rebuild the MCP server with pnpm --filter @dfai/mcp build, then restart it — in Claude Code start a new session; in Claude Desktop quit and reopen it.
