Types and properties

A type is a kind of note — Task, Project, Person — with its own properties. Types live as files in .atlas/types.

  1. Press + next to Types in the sidebar, give it a name and an icon.
  2. Open the type's definition with Edit type — see Edit a type below.
  3. Add properties, choose each kind, drag to reorder, tick Required on new notes on the ones every note should have.
  4. For a Relation, choose the type it points at, and tick Allow many for it to hold several notes.
  5. For a Thumbnail, nothing more to choose: each note of the type gets a picture of its own page (see Thumbnails). A type can have only one.

Edit a type

Clicking a type in the sidebar opens its views, not its definition. The type itself is edited in the right sidebar's Type tab, beside its notes. Any of these opens it:

  • The gear at the end of the type's view tabs (Edit Task type, for Task). The view stays where it is, with the editor beside it.
  • Edit type in the bar of the type's own page. It stays pressed while the editor is showing; press it again to put the sidebar away.
  • Right-click the type in the sidebar (or focus it and press ⇧F10) → Edit type. The same menu has Open.
  • Search ⌘K: type edit and pick Edit <type> type, e.g. Edit Task type. These only appear once what you type starts with “edit”, so they never crowd out notes.

Each of these places also has Edit template, for what new notes of the type start as — see Templates.

The editor shows the type's icon and name at the top — click the icon to choose another, click the name to rename it. Below, its Properties, with how many there are. Each row shows the property's name and kind — a relation by the type it points at, Person, many — and its arrow opens it in place:

  • Name and Kind, and for a relation Points at.
  • Allow many — for a select, a relation: several values instead of one. A select that allows many is a multi-select.
  • Required on new notes — written as required: true in the type's file. It never stops you saving a note: an empty required property just says “Date is required” under it until it is filled.
  • Stored as — the key the value is saved under in each note's file.

At the bottom, Template and Default view open what new notes start as and the type's first view, and the foot says Saved · edits apply to every Session note: every change is written to the type's file straight away, and nothing else in that file is touched. The sidebar follows the page: open another type and it edits that one. In a window too narrow for the sidebar (under about 1060px with the left sidebar open), asking for the editor hides the left sidebar to make room.

Options for select properties

Rename, reorder, colour and remove options — for example a project's statuses planned, active, paused, done. (A task's eight GTD statuses are moved to all at once, from the Inbox.) Renaming an option asks “N notes use ‘review’…” and offers to update them. Order sets the order of a board's columns and lanes, and of a table's groups. The Done option decides which status a ticked checkbox sets.

Colours. Every option is a muted pastel pill, so a column of them is easy to scan. A status (Doing, Review, Done…) keeps its own colour and dot. Any other option — a meeting's Interview or 1on1 — gets a colour from its name: the same name is always the same colour, in a table, on a board, in the properties panel and on cards. To choose one yourself, pick it from the option's colour menu: one of the status colours, or gray, brown, orange, yellow, green, blue, purple, pink or red. In the type file it is written as colors: { Interview: blue }. Linked notes (a meeting's Larkspur Payroll or Mara Quill) and #tags are coloured from their names the same way.

A type file with a mistake in it

A typo in a file in .atlas/types never costs you the other types: they still load, and that file is listed under Types in the sidebar by its name, with what is wrong below it. Click it to open the file and mend it; once it reads, it leaves the list.

  • Its frontmatter is not valid YAML: and what the parser says is wrong, with the line and column — an unclosed [, a tab for an indent.
  • Its frontmatter has no closing ---. Without it, none of the block is read.
  • Its frontmatter is not a set of properties. It reads as a list, or as one value, where a type is key: value lines.
  • It has no name, and a type needs one. The type is not loaded until it has a name:.
  • Its property “pages” has a kind DFAI does not know: “nmber”., or …is a relation that names no type to point at. The type still loads, without that property.

A file there with no frontmatter, a blank one, or frontmatter with none of a type's keys (name, label, properties, icon, folder) — a README, say — is left out without a word.

Built-in types

Person, Task, Project, Artifact, Meeting, Company, Term, Proposal, Decision, Block and Daily are marked Built in: DFAI's own features depend on them. In the type's editor their Delete button is turned off, with the reason beside it — for example “Person is built in — @ mentions find people by it — so it cannot be deleted. Its properties are yours to change.” Their properties stay yours to edit. Their files in .atlas/types can't be deleted or renamed from Pages either, whatever the file is called: “DFAI’s built-in types stay — its features depend on them.”

A type you made has Delete <Type>… under its properties in the type's editor; it asks first, as deleting any note does, and puts the type's file in the Trash.

Projects

DFAI ships a Project type (status: planned, active, paused, done; owner; due; summary). Every task has a project relation — to a project or an area, once your types are set up for PARA — and the Projects view is a board grouped by project.
