Automations

A rule that tidies the vault while you work: when it runs — on a clock, or when a note of a type appears or changes — which notes it takes — an DFAI query — and what it does to them: archive them, set a property, or ask Claude to propose things. Every run is logged and can be tried first as a dry run. The last run that archived or set something can be undone.

Where they are

  • Automations is in the sidebar, under Tags. It opens a page listing every rule.
  • Each rule is a note in .atlas/automations, under System in Pages. Its frontmatter is the rule; anything you write in its body is your own notes about it.

Start one

  • Archive done tasks after 30 days, the ready-made one, sits at the top of the page. It opens in the editor for you to look over; nothing is made until you press Create automation. It runs every day at 03:00, takes FROM task WHERE status = done, only notes not changed in the last 30 days, and archives them.
  • After a meeting, another ready-made one, asks Claude about each meeting of the last 14 days that arrives (FROM meeting WHERE date >= @-14d) with its own prompt, .atlas/prompts/after-a-meeting.md, which DFAI writes once when you create the rule and never over yours. It is the step that says Make into tasks: My own action items, so it asks claude-sonnet-5-5 on its own budget, and your own action items become tasks without a click — see What happens after a meeting.
  • Friday review drafts your weekly review every Friday at 15:00, as one new note in Reviews/: what got done, what is stuck, what to decide. Claude is handed the weekly review itself — the tasks you finished and the meetings you had this week, who has not come back to you, what is overdue, projects with no next action, and what waits in the Inbox — and every line of the draft links the task, project or meeting it is about; a line that links none is left out, and the log says which. It writes one draft a week: Run now again that week makes nothing. Its prompt is .atlas/prompts/friday-review.md, yours to edit.
  • Morning brief writes a pre-read for each of today's meetings with a linked person or company, every day at 07:00, into Inbox/Briefs/. See Morning brief.
  • New automation starts a blank rule, taking every note of your first type.

The editor

Click a rule's name to open it above the list.

OnWhether it runs on its schedule.
WhenDaily at a time, Every few hours (every 1 to 168 hours), When DFAI opens, By hand, or When a note appears: a type, then is created, is changed or both — one stays ticked. See When a note appears.

Below the fields: Create automation or Save, Dry run, and, on a saved rule, Run now and Undo last run; Cancel or Close leaves it. A rule that can't be saved yet says why in red, like “Name the automation.” Under the buttons is the rule's Log, newest first.

The list

  • Each rule has a switch (Run <name> on its schedule), what it does and when (Archive · Every day at 03:00), Last run with what it did, Next run, and Run now.
  • Next run shows — for a rule that only runs when DFAI opens, by hand or when a note sets it off, one that is off, and one paused until it is run by hand.
  • Turning a rule on is logged as Turned on, and its schedule counts from then.
  • A rule held up says why beside it: “Paused: Its log could not be written (…). Run it by hand to try again.”, “Could not run (…); it is tried again at 14:05.”, or “Its log has an entry dated …, later than now; its schedule counts from before it.”
  • A rule whose file is wrong is listed too, never run, with why: “This rule’s file cannot be read: Write enabled: true or false.” Fix the file and it is read again.

When a note appears

A rule can wait for a note instead of a clock: File standups — when a meeting is created, take FROM meeting WHERE kind = standup, and archive it.

  • is created sets it off for a new note of that type, however it came: typed in DFAI, written through the Local API, saved by another app, or brought in by a sync pull — including one that arrived while DFAI was closed, once the vault is open again.
  • is changed sets it off each time a note of that type is saved with different text.
  • Neither is set off by a note moved, renamed, archived, or put back from the Archive — even if a note of the same name now stands where it was put back, and it comes back as Standup 2. A note in the Archive never sets a rule off.
  • An arriving meeting is created when the meeting import lets it in: the rule runs once, on the version stamped imported, the import's own line is never a change, and a meeting it refused or archived as a second copy never sets a rule off.
  • It acts only on the notes that set it off, and only if Which notes matches them too. The rest of the vault is left alone.
  • Once per version. The log records each version of a note the rule handled, and the version its own change left, so none of them sets it off again: not after a restart, a rebuilt index, or the same file pulled twice. Change the note again and it runs again.
  • When a note the rule has handled leaves its path — deleted, moved, renamed or archived, by you or by the rule — the log says it went: a new note made later at that path, even from the same template, is new to the rule. That holds when one pull brings both, the old one archived and a new one in its place.
  • A note whose links an archive rewrote is heard again, as anyone's edit would be — it may have been edited too. If the rule finds it as it leaves it, nothing is written.
  • A run that changed nothing isn't logged: one with nothing to do says nothing, and one that left a note alone — open with unsaved typing, say — says so in Activity only, and runs again when the note is next saved.
  • 20 runs an hour at most, per rule, counting runs that changed a note or whose query didn't read — two rules setting each other off can't run forever, and typing in a meeting doesn't use it up. Past that it is held, once: “Held back: It has run 20 times in the last hour, the most a rule may. It runs on what changed meanwhile at 10:15.”
  • Held or failing, a rule keeps what it heard — the last 20 syncs — and runs on it once its pause ends. Anything older is let go, and DFAI says so within the minute, in Activity and in the rule's log: “File standups: Let news go. Let go of the news of 3 syncs: more arrived than it holds while it cannot run. Run it by hand to take the notes they named.” Run now takes them.
  • Quit before it ran? What a rule has heard and not yet run on is kept only while DFAI is open. So each time a vault opens, a rule set off by a meeting being created looks for meetings let in since the rule was last saved that its log holds nothing of, and runs on them once, within the same caps. A meeting that was there before you saved or turned on the rule is left for Run now.
  • With sync on, it runs on the same one Mac as scheduled rules. On any other Mac nothing happens; the note waits until that Mac has pulled it. Until DFAI knows which Mac this is, what it hears is held. A rule that asks Claude also waits for a pull, as below.
  • Dry run lists the notes that would set it off now: those Which notes matches whose current version it hasn't handled. Run now takes the same notes — a way to catch up on ones it skipped while paused, or that were there before the rule.
  • In Activity its line names the notes: “File standups: Ran when a note appeared or changed (Standup). Archived 1 note.”

Ask Claude

A rule can ask Claude to read its notes and propose things. Claude never edits a note this way: it only writes proposals for you to accept, or one new note. Example: Meeting actions — when a meeting is created, ask Claude to find the action items, and propose each one as a task.

  • The prompt is a note in .atlas/prompts/, like .atlas/prompts/meeting-actions.md. Its body is what you ask; write it like a note to a colleague. In the editor you can type just its name, meeting-actions.
  • Or a skill. In the editor, Asks with picks A prompt note or one of your skills, like Skill: meeting-actions; with a skill picked, the prompt path goes away. A skill that would fail the run says so beside its name, (has problems) or (too long to run). The rule's file then says skill: meeting-actions and no prompt: — a rule that says both isn't run, and says “Name one: prompt: .atlas/prompts/<name>.md, or skill: <name>, not both.” Claude is handed the skill's instructions, the body of its SKILL.md, never its name or description. A skill that's gone, or that the Skills page shows a problem for, fails the run with nothing asked or written: “Its skill meeting-actions is not in .atlas/skills.”, or “Its skill meeting-actions cannot be used: Say what the skill does and when to use it.” A run hands Claude at most 20,000 characters counting an emoji as two, as for a prompt note, so a skill the Skills page accepts — which counts an emoji as one — can still be too long to run.
  • What it writes: Proposals in the Inbox — each one a task, decision, follow-up, person, term or project for you to accept, edit or reject, citing the line of the note it came from, like [[2026-10-01 Standup#^t0003]], with a confidence. Or A meeting's actions and decisions, as proposals (output: meeting-items) — see What Claude pulls out. Or the same with a summary of the meeting beside them (output: meeting-digest), which After a meeting writes at the top of the meeting. Or One new note in a folder you name, like a morning brief: never written over. On a daily or weekly schedule it writes one note each time the schedule comes round, however often it runs: run it again that day (or that week) and it makes nothing, and its log says the note is made already. A rule that runs by hand or every few hours makes a new note every run, numbered past one already there (Morning brief 2).
  • Tools Claude may use are some of the chat's read tools, like atlas_read_note and atlas_search. It's handed the notes the run is about either way. With none ticked, it reads only those.
  • It reaches Claude the way the chat does: your own Claude Code, or the API key, and the model chosen in Settings → Claude — unless the rule names its own in Model (model: claude-haiku-5-5). Leave it blank for the default, which the box shows.
  • Make into tasks (apply: mine), offered for output: meeting-items and output: meeting-digest: My own action items marks the step that writes a summary at the top of each meeting and turns your own action items into tasks, linked to the meeting, without a click; everything else stays a proposal (see What happens after a meeting). A rule saved with meeting-items is read as meeting-digest, so it summarises too. Such a step asks claude-sonnet-5-5 unless Model names another, at most 10 times a run (a long meeting's parts and the one ask that merges their summaries count together), and up to 30 times an hour on an allowance apart from the 20 runs an hour — so a backlog of meetings never uses up a rule's runs, and they never hold it back. The 30 are one allowance for the whole vault, shared by every rule that says My own action items, not 30 each, and a run never asks past what is left of them: one that starts with a single ask left asks once and says the rest of the meeting was cut. Past 30 it waits, and says until when.
  • It waits for a pull. With sync on, a Claude rule set off by a note, its schedule or opening the vault doesn't run after DFAI starts or the Mac wakes until a pull has finished and the settings still name this Mac, nor while sync is paused here. It checks again after Claude answers, before it writes anything; if the Mac slept meanwhile, nothing is written and it runs again after the next pull. A schedule that comes due while it waits runs at the next pull. Run now doesn't wait.
  • All or nothing. If Claude's answer isn't what the rule asks for, nothing is written and the run fails. That covers an answer that isn't JSON, one with a key it wasn't asked for, a proposal that cites a line the note doesn't have (or one inside a code block, or past where a long note was cut), a tool the rule didn't tick, or no answer within 10 minutes (the whole run, however many asks it makes). Activity says why: “Meeting actions: Ran by hand, and could not. Claude called atlas_search, which this rule does not let it use.”
  • Text and links only. What Claude writes can't load anything from the web when you open it: no ![](https://…) picture, no <img> or <iframe>, no web address as a property's value. An answer with one is refused whole, like any other that isn't what the rule asks for. A link you click is fine. Titles, notes and “why” are kept to a size a person would write, and properties to a few plain ones (text, numbers, true or false, short lists) — never DFAI's own, like type or archived.
  • It can't write just anywhere. Not in Chats/, .atlas, the Archive or the proposals folder, nor deeper than DFAI reads. A rule that names one is refused when it's saved.
  • Stopped part-way? If the disk refuses a write after some proposals were made, those stay, and the log says “Made 1 of 3 notes, then the write failed” with a line for each. Run now asks again and finishes the rest: a proposal already made, answered or archived is never made twice — it is known by the rule, its kind and title, and the line it cites (for a meeting, the meeting itself, wherever it has been filed or renamed), however Claude wrote the link. A run that finds them all made already says “Nothing new to propose (2 already made).”
  • Two notes with the same title? If a run reads both and Claude cites one by its title alone, the answer is refused and says to cite by path, like [[Meetings/Alder/2026-10-06 Weekly#^t0001]]; DFAI never picks one.
  • Claude Code not installed or not signed in? The run fails with the same fix the chat shows: “Claude Code is installed but not logged in. Fix: claude auth login.”
  • Activity names the model and how long it took: “Meeting actions: Ran when a note appeared or changed (Standup). Made 2 proposals. Asked claude-opus-5-5, 4.2 s.”
  • A long note is read in part. (A meeting read with output: meeting-items is instead read in parts, to its end.) Claude is shown about the first 20,000 characters of a note (less when a run reads several), and the log says so: “1 note was too long to read whole: Claude saw only the start”, with a line saying how much, like - cut "Meetings/2026-10-01 Standup.md": read 19874 of 48211 characters. A meeting is cut between turns, never in the middle of one, and a proposal can't cite a turn Claude wasn't shown.
  • On a meeting that arrives (when a meeting is created), Claude is asked once, about the meeting as DFAI let it in: checked, its misheard names put right and its people linked — never the file as it landed. A second copy of the same meeting asks nothing. A rule on meetings that change isn't set off by any of that, only by an edit afterwards. The proposals Claude makes never set its rule off.
  • 10 notes a run at most, because Claude reads each one. If more match, the log says “Read the first 10 notes, the most one Claude run takes; run it by hand for the rest”, and Run now takes the next ones. A note it was asked about counts as handled, even if it proposed nothing, on a clock or when a note sets it off alike, so the same version isn't sent again until the note changes. That holds wherever the note goes: a meeting filed or renamed out of the Inbox, its text unchanged, isn't sent again — not by Run now either. A failed run handles nothing: Run now asks again.
  • It counts toward the hourly cap of a rule a note sets off — each time Claude was asked, including an answer of nothing and a failure, so a long meeting read in four parts counts four. A run that never asked (a prompt over 20,000 characters, Claude not signed in) counts nothing.
  • It never reads a proposal, since it would only be answering itself. DFAI's own files are skipped too.
  • A rule can't say a Claude step edits a note. Anything but output: note, output: proposals, output: meeting-items or output: meeting-digest — edit, say — or a note named by path:, is refused: “… A Claude step never edits a note: it writes proposals for you to accept, or one new note.”
  • Dry run lists the notes it would ask about, without asking Claude. Its run can't be undone; answer its proposals in the Inbox instead, and keep or delete a note it made.

Dry run, run, undo

  • Dry run says exactly what the rule would do now — “Would archive 12 notes.” or “Nothing to do right now.” — then lists each note it would take (click to open) and each it would leave, with why. It changes nothing, and works before a new rule is saved.
  • Run now runs it at once, on or off, whatever its schedule. Afterwards Last run says what it did: “Archived 12 notes. Left 1 alone.”
  • Undo last run undoes the newest run that archived or set something, once. It can't reach further back: that would put back notes later runs have acted on since.
  • It reverses only what that rule did: notes it archived go back where they were, and properties it set go back to what they held.
  • What has changed since is left as it is and listed: a property changed again, a note moved out of where the run put it, or an archived note whose archive stamp isn't the run's.
  • The log is a note anyone could edit, so a line the rule couldn't have made — an archive in a rule that sets, a key it doesn't set, a value no property holds — is skipped and listed, never carried out.

When they run

  • DFAI checks the rules when a vault opens, once it is indexed, then every minute while it is open. Nothing runs while DFAI is closed.
  • A daily or hourly rule whose time passed while DFAI was closed catches up once when it opens, however many times it missed.
  • With sync on, rules run on their schedule, or when a note sets them off, on one Mac only — the one that set up sync first (a Mac connecting later never takes them), until you turn on Run automations on this Mac on another.
  • A daily or hourly rule that is on but has never run or been turned on here — written by hand, or synced in — is marked First seen in its log, and its schedule counts from then, so a daily rule runs by the next day.
  • A mark in the log dated later than now — a clock that ran ahead, or a log synced from one — is ignored, and the rule says so.
  • A rule that keeps failing waits longer each time before it is tried again: 1, 2, 4, 8… minutes, up to 6 hours. A run by hand tries it at once.
  • If its log can't be written, the rule is paused until you run it by hand, rather than change notes nothing records.
  • One run at a time; a save from the editor waits for a run under way, never dropped.

Safe by design

  • At most 500 notes are changed in one run (10 for Ask Claude). Past that it says “Stopped at 500, the most one run may do; the rest wait for the next run.” Notes already as the rule would leave them don't count.
  • A note open with unsaved typing is left as it is and logged: “It is open in DFAI with unsaved typing, so it was left as it is.”
  • A rule only acts on its own vault. Open another and the run stops: “Another vault was opened, so the automation stopped.” What it did up to then is logged.
  • An archive rule never touches notes already archived, even with INCLUDE ARCHIVED. It archives by the same rules as the app, updating links as it goes.
  • DFAI's own files in .atlas are never changed by a rule.
  • A connected Claude can read the rules and their logs and dry-run one, but never run, undo, turn on or off, make or change one — that stays on this page.

The rule's file

A rule can be written or edited by hand, anywhere. Its frontmatter:

atlas: automation
id: Archive done tasks after 30 days
name: Archive done tasks after 30 days
enabled: true
when: daily at 03:00
which: FROM task WHERE status = done
olderThanDays: 30
do: archive
KeyHolds
atlasautomation, which makes the note a rule.
idWhat its log is named after. DFAI writes it in when it first reads a rule without one, so renaming the rule keeps its history, and a new rule with a deleted one's name starts its own log. Two rules can't share one.
nameWhat the list calls it; the file's name if left out.
enabledtrue or false, nothing else — yes or 1 makes the rule broken rather than quietly off.
whendaily at HH:MM, a day of the week like fridays at 15:00, every N hours (1 to 168), on app open, manually, or a note: a meeting is created, a meeting is changed, a meeting is created or changed (an before a vowel).
whichA DFAI query: FROM task WHERE …
olderThanDaysOptional: only notes not changed in this many days, 1 to 3650.
doarchive, set with the values under set:, like set: {status: done}, or claude.
promptFor do: claude: the prompt note, .atlas/prompts/<name>.md.
skillFor do: claude, in place of prompt: a skill's name, like skill: meeting-actions. Never both.
toolsFor do: claude: a list of read tools, like [atlas_read_note, atlas_search]. Optional.
outputFor do: claude: proposals, or note with the folder under folder:, like folder: Briefs. Not .atlas, the Archive, Inbox/Proposals or Inbox/Meetings.
  • What set may write: plain values — text, a number, or true / false. 007 stays text, so a code keeps its zeros.
  • What it may not touch: type, id, any key starting with atlas, and the Archive's stamps archived, archivedFrom and archivedPrior: “A rule cannot set “type”: DFAI keeps that one itself.”

The log

  • One file per rule, .atlas/automations/log/<id>.md, headed <name> — run log. Each run, undo, Turned on and First seen is a ## section, newest last: when, what happened, then one line per note changed or left and why.
  • A run a note set off also lists - triggered by "…" at "…" for each note version it handled, - wrote "…" at "…" for the version its own change left, and - went "…" for a path a note it had handled left. That is the rule's memory of what it has done: delete those lines and it may act on those versions again.
  • A Claude step's run lists - proposed "…" for each proposal, - created "…" for its note, and - claude "<model>" in "…" ms, with a - cut "…" line for each note it read only the start of, - asked 3 times when a long meeting was read in parts, and a - dropped "…" line for each item it left out. What Claude wrote itself, like a reason it failed, is cut to a few hundred characters.
  • It's meant to be read. You can add your own sections, like ## Notes; DFAI keeps them.
  • It keeps the latest 100 entries, and no more than 256 KB; the oldest entries go first, never your own sections.
