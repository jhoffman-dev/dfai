Meetings

Your meeting notes come into the vault by themselves. A meeting is a note of the Meeting type, one markdown file per meeting, with the transcript split into turns you can link to and quote.

How a meeting arrives

Gemini's meetings come as below. Granola's are pulled by DFAI itself — see Meetings from Granola.

  1. The meeting ends and Google Meet's “Notes by Gemini” email lands, as it always has.
  2. n8n, on your work computer, reads the email and sends the meeting two places from the same step: to Notion's Meeting Notes, as before, and to DFAI's Local API (POST /v1/meetings) on the Mac.
  3. DFAI writes it into the vault you have open, as one markdown file in its month, Meetings/<year>/<month>/<date> <title>.md — for example Meetings/2026/09/2026-09-29 Platform weekly sync.md. A second meeting with the same name that day goes beside it as … (gemini 1a2b3c4d).md. This needs DFAI open, with the Local API on.

DFAI never logs in to Gmail, Notion or the notetaker; n8n hands it the meeting. The two sends don't wait on each other: if Notion's write fails, DFAI still gets the meeting, and if DFAI can't take it, Notion still has it. n8n tries DFAI three times, five seconds apart, then emails you “This meeting did not reach DFAI” with why — usually DFAI was closed or the Local API off. Open it and re-run that execution in n8n. Sending a meeting again is safe: if the vault already has it, DFAI says so and writes nothing. DFAI checks a meeting against the import contract before writing it, so one it would refuse is never written. A meeting with no start DFAI can trust — no time in the email's subject, and no transcript length to count back from when the notes arrived — is refused, never guessed.

What DFAI does when it arrives

Once the file has arrived, DFAI checks it against the meeting import contract (the same check as pnpm validate:meeting below). It then writes one line saying what it did, atlas_import_outcome:, right under the file's atlas_import: meeting/v1 line, and does one of three things. Each is one line in Activity, under Meetings.

It's fine — imported

That line is the only thing the import writes; the rest of the file is as it came. DFAI then links it to who was there. It stays in its month folder and shows in the Inbox until you file it under a project or an area, or archive it. Activity: “2026-09-29 Platform weekly sync: arrived in the Inbox.”

It's a second copy — duplicate

Same provider and provider's id as a meeting already in the vault, wherever it is, even one you filed or archived. The copy goes to the Archive and is marked there with a link to the one kept, by its path: atlas_duplicate_of: "[[Meetings/2026/09/2026-09-29 Platform weekly sync]]". Activity: “… a second copy of 2026-09-29 Platform weekly sync, so it was archived.”

A meeting already imported is always the one kept. Of two that arrive together, the one at <date> <title>.md is kept over the one written at … (gemini 1a2b3c4d).md because that name was taken.

Something's wrong with it — error

It stays where it landed. Nothing in it is fixed or deleted. DFAI writes at the top why it failed, the first few problems with line numbers:

atlas_import_error: "external_id is required; Transcript: Line 15: the turn has no block id — end it with ^t0001 and so on"

It shows in the Inbox with that error beside it (and as Import error in its properties). Activity gets a warning: “2026-10-02 Vendor call: could not be imported. external_id is required”.

  • Fix it in place. Correct the file in DFAI and save. DFAI checks it again, takes atlas_import_error out, and stamps it imported. Activity: “… now follows the import contract, so its import error was taken out.” To see every problem, not just the first few, run pnpm validate:meeting on it.
  • Or send it again. Fix what n8n sends, then re-run that execution. A file with an import error doesn't count as having the meeting, so the new copy is written beside it, at … (gemini 1a2b3c4d).md. Delete the broken file first to keep the meeting's own name.
  • Want the copy back? Unarchive it. It keeps its duplicate stamp, and DFAI leaves it alone.
  • Your edits are yours. Once a file has its imported or duplicate line, DFAI never looks at it again. Editing it, adding your own sections, renaming it or filing it under a project is never undone, marked or archived, and it is still the meeting a later copy is matched against. Keep the line: take it out and DFAI sees the file as just arrived.
  • A sync conflict. If both Macs changed a meeting before they synced, sync keeps this Mac's version and puts the other beside it as … (conflict from Mac).md. DFAI never imports or archives that copy. Activity warns you about it once while DFAI is open (again only if the copy changes): compare the two, keep what you want, and delete the copy. A file DFAI can't read or write is said once the same way.
  • One Mac does it. Only the Mac that runs your automations imports meetings. Any other Mac leaves them alone, and says so: see the next point. After you move the automations to the other Mac, both may import until the first Mac next syncs and reads that: they come to the same answer for every file, and sync keeps both if they write the same file.
  • The other Mac tells you what waits. On a Mac that doesn't run the automations, the Inbox shows a line at the top, like 3 meetings waiting for Studio, naming the Mac that does by the name in Settings → Sync. It counts meeting files that have no atlas_import_outcome line yet, and meetings already let in, from the last 14 days that the rule's own query takes (DFAI asks the index, so a rule narrowed to standups counts only standups; undated meetings never count), whose summary and tasks are still pending — the After a meeting rule hasn't finished them, because its Mac couldn't reach Claude or a run stopped part-way — so a Mac whose Claude is logged out never looks as if nothing waits. A sync-conflict copy and a file DFAI can't read are never counted, since moving the automations wouldn't clear them. Activity warns when a number first appears and when it changes to one it hasn't shown yet that session, not at every sync. Until a sync has finished since DFAI started or the Mac last woke, the line gives no number: Meetings may be waiting for Studio: they are counted after the next sync. While sync is paused it says they are counted once sync resumes. There is no line when none wait, when the vault has no meeting files at all, or on the Mac that runs the automations. To process them here, press Process here on that line.
  • Process here. The button makes this Mac the one that runs the automations, as Run automations on this Mac in Settings → Sync does, then syncs at once. Until a sync has sent the change to GitHub, the line says “Process here is set on this Mac but not yet shared with Studio.” and nothing runs here yet, since Studio still thinks it is in charge; with sync paused, that waits until you resume. Once that sync finishes, this Mac imports every meeting that waited and runs the rules that missed them; the line goes, and Activity says “Laptop now runs the automations: meetings that waited are processed here.” The other Mac stops at its next sync and shows the line itself when new meetings arrive. The button is greyed out, and the line says why, while sync is paused on this Mac, while its last sync failed, or until a sync has finished since DFAI started or the Mac woke: otherwise this Mac could name itself in settings the other Mac never sees. If the vault's settings can't be read, nothing is changed and the line says so. Pressing it on two Macs before either syncs leaves one of them in charge: the one whose sync comes second keeps its own claim, and the other's is kept in Sync conflicts/. Nothing moves the automations by itself.
  • It waits for a pull first. With sync on, after DFAI starts or the Mac wakes, nothing is imported until a sync (or a look at GitHub that finds nothing new) has finished, and only if the settings it brought still name this Mac. So a Mac that was asleep while the other took over finds out before it writes anything. A meeting file that changed on this Mac after the last pull, like one this Mac's own Granola pull just wrote, waits for the next pull, a minute or so by default. DFAI checks again right before it writes each file.
  • Paused or unreadable, it waits. While sync is paused on this Mac, nothing is imported; Settings → Sync and Activity say so. If .atlas/settings.md can't be read (missing after a pull, or broken), nothing is imported until it can be; Activity says that too.
  • After each pull, once its index is ready, the importing Mac settles every meeting file without the line: each in a month folder that says atlas_import: meeting/v1, and every file in Inbox/Meetings. That includes files that came while it was closed or asleep, and files it couldn't finish (you were typing in it, or its frontmatter wouldn't read); Activity says which. Hidden files there are left alone, as everywhere in DFAI.
  • Only those are checked. A meeting you make yourself in a month folder is just a note, and no import line is written into it. So is a meeting filed some other way, like Meetings/From Notion. Inbox/Meetings is still read, file by file: an n8n workflow you haven't re-imported keeps writing there.
Your own vault's Inbox. Meetings are imported in any vault. Whether the Inbox lists them depends on the vault's Inbox view and Meeting type, which DFAI doesn't change for you yet. The vault in the DFAI repository has both. In yours, copy its .atlas/views/Inbox.md over your Inbox view. Then, in Edit type, add three properties to your Meeting type: atlas_import_outcome (select: imported, duplicate, error; “Import”), atlas_import_error (text, “Import error”) and atlas_duplicate_of (relation to Meeting, “Duplicate of”). Until then, the files are in their month folders under Meetings/, and Activity lists every one.

Misheard names, put right

As a meeting is let in, DFAI puts right the spellings your Terms say it mishears — and only those: a term's, a person's or a company's Misheard as. A person's or company's Also spelt is for linking people and is never used to change text. Say you have the term Larkspur Pay, misheard as Lark Spur Pay, and the term Mara Quill, misheard as Mara Quil: a turn reading “**Mara Quil** … Lark Spur Pay is ready.” arrives as “**Mara Quill** … Larkspur Pay is ready.”

  • Only the Summary, Notes, Provider next steps and Transcript are corrected; the title and anything above the first section are left as they came.
  • Whole words, exactly as the term writes them — capitals included. A variant Lark Spur Pay corrects Lark  Spur Pay (any run of spaces, never across a line break) and Lark Spur Pay's keeps its 's; lark spur pay, LARK SPUR PAY and Lark Spur Payroll are not touched. So a common word is safe: a variant Pay never changes pay. If both lark spur and Lark Spur turn up, list both. A name already spelt right is left exactly as written, even when a line break or emphasis falls inside it (**Mara** Quill is not turned into Mara Mara Quill), and a spelling two notes disagree about (a conflict on the Terms page) is never corrected.
  • One thing at a time. A word joined to another by -, ., /, @ or \ — an email, a web address, a file path, quill-based — is left alone, and C# is not found inside C#sharp. Where two misheard spellings run into each other (Lark Spur and Spur Pay in Lark Spur Pay), only the first is put right; list the whole Lark Spur Pay too to get both words.
  • Never inside a [[link]], a markdown link or URL, a #tag, code or a fenced code block, a comment, or a ^block-id.
  • Recorded on the meeting. Its frontmatter gets atlas_corrections: — each change, with from, to, count, the blocks (turn and paragraph ids) it was made in, and at, where each one stands — and two checks, atlas_corrections_digest: of the body as corrected and atlas_corrections_original_digest: of the body as it was. Activity's line for the meeting says how many: “2026-09-29 Platform weekly sync: arrived in the Inbox. 2 misheard spellings corrected; Undo corrections on the meeting puts them back.”
  • A meeting with nothing misheard is not changed. If you have terms with misheard spellings, the same write adds atlas_corrections: none so the meeting is never read again; if you have none yet, nothing is added, so terms you add later still apply.

Undo corrections

A corrected meeting's page has a band under its bar: Corrected · 2 spellings put right on import, then each change, the old spelling struck through — Lark Spur Pay → Larkspur Pay ×2. Undo corrections puts every original word back, byte for byte, and sets atlas_corrections: undone, so the band goes and the meeting is never corrected again. Claude's summary at the top of the meeting doesn't count as an edit: Undo works around it and leaves it as it is. If the meeting was edited since, Undo says so and turns itself off; Dismiss hides the band for now (it comes back when the meeting is opened again).

  • Refused if the meeting's text changed since, as an automation's Undo is: “The meeting changed since its words were corrected, so they were left as they are.” Putting the old words back into text you've since edited could undo your edit. Changing its properties — a tag, a project — doesn't count. Anything you've typed is saved first, so it counts.
  • An atlas_corrections list edited by hand into something DFAI didn't write is refused too, and nothing is changed.
  • Corrections are read through the Local API as the meeting's properties (GET /v1/notes/{path}). Undo stays in the app: it rewrites a note you're reading.

Who was there: people, companies and the project

As a meeting is let in, DFAI links it, so clicking a person or a company shows their meetings. The links, the corrected spellings and the imported line all arrive together: an automation set off when a meeting is created runs once, on the meeting already linked and corrected. What it's sure of it writes into the meeting; what it isn't sure of waits in the Inbox as a proposal. It never guesses.

  • People, by email first. An attendee whose address is a person's email, or one of their other_emails, is that person — mara@larkspur.example is Mara Quill whatever name the notetaker wrote. With no match by address, DFAI tries the name, then their Also spelt aliases, ignoring case and spacing — the same way the Terms page compares spellings. Everyone it finds is added to the meeting's People.
  • Speakers too. A named speaker in the transcript who is exactly one person is added as well, by the name your Terms correct it to: a turn heard as Tobias Fen, which a term puts right, links Tobias Fenn. You and unknown speakers are left alone.
  • Companies, by email domain. An attendee at larkspur.example links Larkspur Payroll when the company lists that domain in Email domains (or its Site, when that is the site's front page rather than a page below it). If two of your companies list domains that both fit, the more specific one wins, so a subsidiary isn't taken for its parent. Gmail, Outlook and the like never count, in any country, and neither do sites like YouTube, LinkedIn or yourco.zendesk.com. A person's own Company is linked too. Two companies claiming one domain at the same depth link neither.
  • A company only a domain's name points at is proposed, not linked. If fenn.example looks like a company called “Fenn” that lists no domain of its own, it waits in the Inbox as a link proposal on the meeting's Companies for you to accept.
  • Someone new is proposed, not made. An attendee DFAI can't find waits in the Inbox as a Person proposal with their name, email and the company their address is at. Accept makes them in People/ and adds them to the meeting's people: the card says “And adds it to people of 2026-10-06 Payroll sync.” If you already accepted them from another meeting, accepting here just links them; if you filed the meeting since, it's still found — by its id, not its old place. If it has been archived instead, DFAI says so and writes nothing. Reject someone once and they aren't proposed again from later meetings.
  • Two people with one name or alias — two Tobys — is never a guess: each is proposed as a link on the meeting, low confidence. Accept the one it was and reject the other.
  • Group addresses are never people. payroll-team@larkspur.example stays in the attendees and is never proposed. Neither are you: an attendee with your profile name — however it's written, even “Last, First” — or one of Your emails is left out. If the one person of an attendee's name has other addresses on file, DFAI proposes the link instead of making it.
  • The likely project. If the meeting has no project, DFAI proposes the open project most tied to its people and company — one they own, link, or met about before — and names the runners-up on the card. It's always a proposal; only you set a meeting's project.
  • Once per meeting. DFAI links a meeting as it's let in, and never again: take someone out of its people and they stay out. It only ever adds — nothing already linked is changed — and a proposal you rejected isn't made again. A meeting you're typing in is left alone, and Activity says so: “2026-10-06 Payroll sync: linked Mara Quill, Larkspur Payroll; proposed 1 in the Inbox.”
  • When linking fails. If DFAI couldn't link a meeting as it arrived — the index was rebuilding, say — the meeting is let in all the same, Activity says “Could not link the meeting: …”, and the meeting carries atlas_links: failed. A Dry run of After a meeting lists it under Not linked — “1 meeting is not linked: Run now links it first.” — and Run now links it before Claude reads it, taking the line out in the same save. Only a meeting whose linking failed is linked again, so one already linked is never touched, someone you took out stays out, and running it twice links nothing twice. Once DFAI has written any link into the meeting it counts as linked, even if it had to leave a field you wrote yourself. If it couldn't write a link — you're typing in the meeting, your People holds something other than links, or linking fails again — the line stays for the next Run now, and Activity says why each time. Run now takes the newest 50 first. It only reaches meetings the rule's query matches — the last 14 days, as the preset has it — so a meeting still not linked after that needs the query widened, or its people added by hand.

What Claude pulls out

Turn on the ready-made automation Pull actions and decisions out of a new meeting (open Automations, click the button of that name, then Create automation) and each meeting that arrives is read by Claude once it's let in. What it finds waits in the Inbox as proposals. Nothing is written until you accept one.

  • Yours. Something you said you'd do becomes a Task proposal at status: inbox. You are You in the transcript, your profile name (in any common spelling, or just your first name when nobody else in the meeting has it), or an attendee at one of Your emails. We is yours too, marked low confidence so you check it. An item with two owners (You and Tobias) is made once, as yours, and the card names the other.
  • Someone else's. Something another attendee took on becomes a Task at status: waiting, with waiting_on linking their Person note — [[Tobias Fenn]]. If you have no note for them, waiting_on holds their name as text and the card says so: “There is no Person note for Lena Hart yet, so waiting_on holds the name as text.” When the name could be more than one person (two Tobiases in the meeting, or two notes for one name), a group, “Everyone” or “TBD”, nobody is guessed: the task goes to your Inbox with an empty waiting_on, and the card says who it could be.
  • Decisions become a Decision proposal, with meeting linking the meeting.
  • Follow-ups — a question left open, a “let's come back to this” — become a task in your Inbox tagged follow-up.
  • Each one cites the turn it came from. Click [[Vendor contract call#^t0004]] on the card to read what was said. Only a turn of the transcript counts: the notetaker's own next steps are given to Claude as hints, and one is kept only if a turn says it.
  • Under the title, the card says why: “Tobias Fenn took this on in Platform weekly sync, so it waits on them.”
  • Low confidence is marked. The card has a coloured edge and says low confidence when whose it is rests on a guess: the turn was spoken by Unknown or Remote Speaker, or Claude couldn't name anyone, or named someone who isn't in the meeting and has no note. A card is medium at most when someone other than you and the owner spoke the turn, and a decision or follow-up from an Unknown speaker is low. With nobody named, the card has an empty waiting_on: click Edit, set status to waiting and waiting_on to who, then Accept as edited — or accept it as yours.
  • Accept makes the task or the decision and links it from the meeting, under its Tasks or Decisions, so the meeting lists what came out of it. If your Meeting type doesn't have those two relations yet, DFAI offers to add them when the vault opens; until it has them, Accept is refused and says why — “… has no relation called tasks to link through.” The run's log and Activity say so too, once, when the Meeting type lacks them. If a note of the task's name is already there (last year's finished one, say), Accept makes yours as Send the notes 2 and links that, never the old one. A waiting-for whose Person note was renamed or deleted since is refused, saying so; Edit its waiting_on and accept again. Undo of an accept takes back both the task and the meeting's link, or neither.
  • An item that is wrong on its own is left out, and the rest are kept: one that cites a turn the meeting doesn't have, or has an owner longer than a name, or a confidence or kind that isn't one. A due date that isn't a date (or is years from the meeting) is left off and the item kept one step less sure, the log saying - adjusted …. One run makes at most 25 proposals; the log says how many it left out. The rule's log names it — - dropped "Order the cake": Platform weekly sync has no transcript turn ^t0099 that Claude was shown. — and Activity says “Left out 1 item of the answer that did not read.” A meeting with no transcript turn isn't asked about at all, and the log says so. Each part of a long meeting also starts with the last two turns of the one before, quoted for context.
  • A long meeting is read in parts, a few thousand words of whole turns at a time, so the end of an hour's call is read as carefully as the start. The log says - asked 3 times. One run asks at most 10 times, within ten minutes in all; past that (several hours of talk) the log says how much was read: - cut "…": read 193709 of 281220 characters.
  • The prompt is yours to edit. Saving the automation writes .atlas/prompts/meeting-extraction.md if it isn't there: what counts as a commitment, how sure to be, how to write a title. Change it and the next meeting is read your way. DFAI never writes over it.
  • To run it on a meeting you already have, open the automation and click Dry run to see which meetings it would read, then Run now.

What happens after a meeting

Turn on the ready-made After a meeting automation and each new meeting is read by Claude once — one run per meeting, on claude-sonnet-5-5 unless you name another model. Claude writes a short summary at the top of the meeting, and the things you plainly said you'd do become tasks by themselves, linked to the meeting both ways. You don't accept anything. What DFAI is less sure of comes as one proposal per meeting to look over, and passing remarks and other people's work don't reach you at all.

  • To turn it on in one go: the Inbox shows Process meetings when they arrive at the top for as long as no rule does it, and Automations always has it above the list. Press Preview and it lists everything it would write, and nothing is written until you press Set up: the After a meeting rule (prompt .atlas/prompts/after-a-meeting.md, output: meeting-digest, apply: mine, meetings of the last 14 days); the prompt itself; on your Meeting type the keys it needs (tasks, decisions, the summary's atlas_summary_* keys, and the import's if you took them off); on your Task type meeting and atlas_item; and Your emails, saved as selfEmails — left empty, nothing is saved and your Person note's addresses are used, or your name alone if it has none; if your addresses were in granola_self_emails, the preview shows them, and saving moves them to selfEmails. Anything already there is listed under Skipped and left as it is (a rule of yours that already says apply: mine, under any name, counts; your own prompt is kept), so pressing it again writes nothing twice. Cancel or Not now writes nothing. Activity lists what was written. A type the vault doesn't have, or that two files define, is skipped and says why.
  • To turn it on by hand instead: fill in your name (and, if a meeting lists you by an address your Person note doesn't have, Your emails) in Settings → Profile, then open Automations, click After a meeting and Create automation. With neither a name nor an address, DFAI can't tell which items are yours, so it makes no tasks, and the Inbox says so at the top — “DFAI can’t tell which action items are yours, so meetings make no tasks for you.” — with Open Settings, for as long as it's true. Each run's log and Activity say it too.
  • The summary at the top. Above the provider's Summary, a callout titled Summary by Claude (claude-sonnet-5-5, 2026-10-14): what the meeting was for and what came of it in a few sentences, the key points, the decisions actually made, the action items that are yours (you (a task was made), or you when they are in your review) and the ones you asked someone else for (Flag the cache before Friday: Tobias Fenn (turn t0002)) — and the questions it left open. It is short on purpose (about 150 words and six key points at most); names are spelt as your Terms spell them. The items are plain bullets, not checkboxes or links: your tasks are under the meeting's Tasks.
  • Yours to edit, never written over. The summary sits between two hidden markers. Running the rule again replaces only its own summary, and only while it is exactly as Claude wrote it: once you edit it, or delete it, DFAI leaves it as you have it and the log says so. The provider's Summary, your Notes and the transcript are never touched.
  • Which items become tasks. One you took on — you spoke the turn it cites, and Claude says it's yours — at high confidence: you said it plainly (“I'll send the contract by Friday”, or “Yes, I can do that” when asked). It lands in your Inbox (status: inbox), with due when a date was said and hasn't passed (a date that has passed is left off, and the task's body says what was said). The summary lists it as yours. DFAI decides this, not Claude.
  • One proposal to look over, per meeting. Your items Claude is less sure of (medium), yours whose turn someone else spoke, yours shared with others (Claude named you and someone else, wrote we where you spoke in the turns leading up to it, or called yours a waiting-for), something you asked another person to do and they agreed to (a waiting-for), and a decision you took part in that Claude is sure was agreed, all go into one proposal: Review what 2026-10-14 Renewal review left for you. Accept it and it becomes one task in your Inbox whose body is a checklist of those items, each linking the turn it came from; reject it and they're all gone.
  • Left out altogether. Anything Claude was unsure of (low confidence); other people's own work you didn't ask for; an item nobody, or more than one person, could be named for (a we should you said nothing around, say); and a decision you took no part in (you didn't speak in the turns leading up to it). The summary lists none of them, and the run's log and Activity count them: “… 1 proposal, left out 12 items.”
  • What isn't an item. The prompt tells Claude, with examples, to leave out work under way, ideas, maybes, questions nobody took on, plans recounted from elsewhere, how things work, and small talk. A meeting with nothing for you makes nothing. DFAI ships that prompt as .atlas/prompts/after-a-meeting.md; if you never edited it, DFAI brings it up to date when the vault opens on the Mac that runs your automations, and Activity says so. One you edited is yours and is left as it is.
  • Linked both ways. The task's source is the turn it came from ([[2026-10-14 Renewal review#^t0001]]), its meeting links the meeting, and the meeting lists it under Tasks — written in the same save as the summary, after the tasks are made, so the summary never lists a task that isn't there. It also carries atlas_item, which is how DFAI knows it made it.
  • Only meetings that arrive after the rule was last saved make tasks. A meeting that was already there — one Run now picks up from the last 14 days — is summarised but makes only the one review proposal, so turning the rule on doesn't fill your Inbox with two weeks of guesses.
  • Never twice. Running it again, Run now, or Claude reading a corrected transcript makes no second task for an item and no second summary: DFAI looks for a task with the same atlas_item in the vault and the Archive, and for a task the meeting already lists that cites the same turn — one you made by hand too. A task you ticked done and archived isn't made again. A proposal left over for an item that is now a task (from another rule, say) is refused on Accept — “… is already a task, made from the same item of the meeting; the proposal was archived and nothing else was written.” — and filed in the Archive.
  • Asked once. Claude is asked about a meeting again only when its transcript changes; a meeting whose summary is already of the words it holds isn't asked about at all. Your edits to its Summary or Notes, and the tasks DFAI links into it, aren't new words. A long meeting is read in parts, and one more ask merges the parts' summaries into one.
  • Stopped part-way? The tasks it made stay, and the log names them. If you were typing in the meeting, or it changed while Claude read it, the summary isn't written yet: the next run writes it from Claude's same answer — it doesn't ask again — and makes only the tasks still missing.
  • When Claude is unavailable. If Claude Code isn't installed or is logged out on the Mac that runs the automations, the meeting is still let in and linked, and the rule's log says the run could not, with the fix. That Mac's Inbox shows one line at the top, “Claude is unavailable on Studio: summaries and tasks are pending for 2 meetings.”, with what fixes it underneath, and Activity says it once — not again each time the rule tries and fails the same way. DFAI checks every minute whether Claude Code says it is logged in, which asks Claude nothing, and as soon as it is, the rule runs on what waited and the line goes. If Claude Code says it is logged in but Claude still refuses (a key that was revoked), it waits instead, as below. It also tries again by itself, a minute later, then waiting twice as long each time up to a quarter of an hour, and whenever DFAI opens. Run now that fails the same way leaves the line as it is. After a restart the line comes back only once the rule's first run fails again.
  • Summary pending. A meeting still waiting for its summary says so on its Inbox row, with why: Summary pending: Claude Code is not logged in. Fix: …, or that the rule hasn't run on it yet. Fix what it says and the rule tries again on its own. The local API and Claude's tools report each meeting's summary as written, pending, edited or none.
  • On one Mac. The rule runs where automations run: the Mac with Run automations on this Mac on (Settings → Sync). No other Mac takes over by itself; on another Mac, meetings wait until you move the automations there. Like every Claude rule it waits for a pull: if this Mac slept or stopped being the one that runs automations while Claude answered, nothing is written and it runs after the next pull.
  • Activity says what it did with each meeting: “After a meeting: Ran when a note appeared or changed (2026-10-14 Renewal review). Summary written by claude-sonnet-5-5 in 41 s for 2026-10-14 Renewal review; 2 tasks made, 2 items listed, 1 proposal, left out 4 items.”
  • Undo last run takes the summary back out, with its keys, while it is still as Claude wrote it — or, when the run wrote over an earlier summary, puts that one back — and moves the tasks it made to the Trash while you haven't changed them. One you've edited stays. If the meeting can't be written (you've edited its summary, or are typing in it), nothing of that meeting is undone and the log says why: no task is trashed while the meeting still lists it.
  • Cleaning up tasks made under the old rules. When tasks this rule made earlier aren't ones it would make now — someone else spoke the turn, or nobody named did — the Inbox offers them: “2 tasks that meetings made aren’t yours by today’s rules.” Review them lists each with why, every one ticked; untick any you want to keep, then Archive. They go to the Archive, never the Trash. A task you untick gets atlas_item_kept: true when you archive the rest or press Not now, and is never listed again. One you changed, finished or moved after the list was shown stays where it is. While DFAI can't tell who you are, it lists none and says why. How sure Claude was isn't kept on a task, so one made at medium confidence before isn't listed.

Suggested terms

Both meeting automations — After a meeting and Pull actions and decisions out of a new meeting — also notice names the notetaker seems to have misheard. Say a turn reads “Send the Bren Wick contract.” and you work with Brenwick Labs: Claude suggests the term Brenwick, misheard as Bren Wick, and it waits in the Inbox as its own Term card, never folded into a meeting's review.

  • Each one cites its turn. The card links the line it was heard in, [[2026-10-14 Renewal review#^t0001]], and says “Heard as “Bren Wick” in 2026-10-14 Renewal review.” What was heard must be in that turn exactly as written, capitals included, or the suggestion is left out.
  • Accept makes the term in Terms/ with what was heard as its Misheard as. From the next meeting on, Bren Wick arrives as Brenwick — see Misheard names, put right. Wrong spelling? Edit the card's title first, then Accept as edited. Meetings already in the vault are not changed.
  • Accept checks your vault as it is now. If, while the card waited, the spelling became a term, person or company, or what was heard became another note's Misheard as (two notes claiming one spelling would leave it uncorrected), Accept is refused and says why — ““Bren Wick” is now a misheard spelling of “Brenwick Labs”; accepted, neither would be put right.” — and the card stays. So it is when a note of the same name elsewhere would lose its [[links]] to the new term, as adding a term on the Terms page is.
  • Everyday words are never suggested as what was heard. DFAI keeps a list of the words meetings are mostly made of (the, file, tomorrow, gonna, and their plurals) and leaves out a suggestion whose misheard words are only those, whatever joins them — follow-up, step 2, mark, all count: a variant is put right wherever it stands as a word, so file as one would change every file anyone mentioned. The right spelling may be everyday words (Team Sync). What was heard needs at least three letters (a vowel sign such as the ा of राम counts as one; in Korean, two syllables are enough), so Q or PR is never suggested. Names in a script written without spaces — Chinese, Japanese, Thai — aren't suggested yet, and the log says why: DFAI can't correct a name inside unspaced text.
  • Nothing you already have. A suggestion is left out when its spelling is already a term, a person or a company, as a right spelling or a misheard one — ignoring capitals, a 's and accents on Latin letters, so brenwick, Brenwick's and Brenwíck are Brenwick. A plural is never taken for the singular: Lucas is a name of its own beside Luca, so it can still be suggested. Letters of other alphabets are never folded: Майя is not Маия. It is left out, too, when what was heard is part of a name you have (Quill, while there is a Mara Quill). A fix of accents or strokes alone is never suggested — Jose for José, Bjorn for Bjørn, Σοφια for Σοφία: the heard form is a real name too, and as a misheard spelling it would rewrite every Jose in later meetings, a different Jose included. To add a misheard spelling to a person, company or term you have, use the Terms page.
  • Suggested once. A term is known by its spelling, so a term you reject is never suggested again, and while its card waits the next meeting doesn't suggest it again. If that meeting mishears it another way (Bren Wik), the card is left as it is and the rule's log says so — ““Brenwick” is proposed already, waiting in the Inbox; once it is a term, add “Bren Wik” to its misheard spellings on the Terms page.” A different term heard the same way as a waiting one is left out too, and the log names the one waiting; so is a second term one answer suggests for the same words, and a second spelling one answer gives for the same term — the log says to add it on the Terms page once the term is made. Two automations reading one meeting at once make one card between them.
  • The log says what was left out, and why — - dropped "Sendthe": “Send the” is everyday words, and would be rewritten wherever anyone says it. — like any other item.
  • If Claude can't be asked, nothing is lost: the meeting was already corrected and linked as it was let in, and stays that way; the run's log and Activity say the step failed and why.
Your own vault's types. Matching reads email, other_emails and aliases on a person, and domains, site and aliases on a company, whether or not your types declare them. The vault in the DFAI repository declares Other emails and Email domains; add them to yours in Edit type (multi-select) to fill them in from the properties panel.

What's in a meeting file

At the top (frontmatter)

title, date, start (and end when known), kind (Notion's Category: Standup, Retro, 1:1…), provider (gemini or granola), the provider's own id, and attendees — each a name and email. A list address like platform-team@… is kept as an attendee marked group: true, and never becomes a Person.

The sections, in this order

Summary, Notes (Gemini's Details), Provider next steps, Transcript. Any can be missing; there's never a section that isn't one of these four.

  • Provider next steps are kept exactly as the notetaker suggested them, one per line: - [Tobias Fenn] Flag the cache: put the new cache behind a flag before Friday. The owner is in brackets; Granola also adds (confidence: high), medium or low at the end. They're suggestions, not tasks — nothing becomes a task by itself.
  • Transcript is one paragraph per speaker turn, with a blank line between turns. Each turn is the speaker in bold, the time, the words, and a block id of its own at the end: 
    **Mara Quill** [~00:00:00] Morning. Shall we start with the cache? ^t0001

**Tobias Fenn** [~00:09:44] Yes. It's ready, but I'd like a flag on it first. ^t0002
    The id is what lets you link to or embed one exact turn — [[2026-09-29 Platform weekly sync#^t0002]] — and quote it in another note.
  • The time. [00:09:44] is the turn's own time; [~00:09:44] with a ~ is approximate — Gemini stamps sections, not turns, so each turn gets its section's time. Gemini's times count from the start of the recording; Granola's are the time of day.
  • Who spoke. A real name as the notetaker gave it; You, which is you — read as your name from Settings → Profile (with no name there it stays You); or Unknown for anyone the notetaker couldn't name (Granola's “Remote Speaker”). An Unknown speaker is never guessed into a Person.
  • Gemini's boilerplate — the disclaimer, “Chat with meeting transcript” links, the transcript's date and end lines — is left out.

Set it up

The full steps are in tools/n8n on GitHub (the README, “API destination”). In short:

  1. Turn on the Local API. Settings (⌘,) → Connections → Local API. It says “Running on port …”; note the port.
  2. Put the token in n8n. Press Copy token. In n8n, Credentials → Add credential → Bearer Auth, named DFAI local API, with the token as Bearer Token. It lives only in n8n's credential store — never in the workflow, the vault or the DFAI repo. After Rotate token, or if DFAI comes up on another port because its own was taken, update the credential or the node.
  3. Add the HTTP Request node. In your Gemini → Notion workflow, wire an HTTP Request node from the step that assembles the meeting, beside the Notion steps. POST to http://host.docker.internal:<port>/v1/meetings, with the DFAI local API credential and a Host header of 127.0.0.1:<port>. DFAI listens only on the Mac itself and refuses any other Host, which keeps web pages out; from n8n in Docker, host.docker.internal is the Mac. Turn on Retry On Fail (3 tries, 5000 ms apart) and set On Error to continue into your failure email.
  4. Send the meeting's fields as JSON. provider (gemini), sourceId (the email's id) and title are required. The rest are optional: subject and arrived (the email's subject and when it came), start and end (HH:MM, when you know them), attendees (each a name and email), summaryMd, transcriptMd, category, and groupAddresses for list addresses that don't look like one. Leave timeZone out and times are read on the Mac's clock; add timeZone: 'America/Los_Angeles' to pin it. Send only these: a misspelt field is refused, naming it, rather than dropped.
  5. Dry run first. On an inactive copy of the workflow, with the Notion writes deactivated (D), run once on a real email. DFAI answers 201 with the file's path and "written", and the meeting is in its month, Meetings/2026/10/. Run it again: 200, "in-vault", nothing written. A meeting with no time in its subject and no transcript takes its start and end from your Google Calendar: the one event that day with the same title that ended before the notes came, within three hours, on your main calendar's clock (so a Mac on a trip still finds the right one). With no such event, or two, it comes back refused — start: the meeting has no start time — saying what to send, by design.

The older route, n8n committing the file to the vault's sync repository with the nodes in tools/n8n, still works while DFAI is closed; the README has it.

Check a file by hand

To see whether DFAI will accept a meeting file — one from the dry run, or one you wrote — run the same check DFAI uses, in the DFAI folder:

pnpm validate:meeting "2026-09-29 Platform weekly sync.md"

ok (with the number of turns) means DFAI will accept it. FAIL lists each problem with where it is — for example attendees[0] must be a { name, email, group } entry, not a line of text.
