PARA and the Inbox

DFAI follows PARA: everything is filed under a Project or an Area, reference is kept as Resources, and finished things go to the Archive. All four are one Project type, told apart by its PARA property. Whatever you capture lands in the Inbox first, to be filed when you process it.

PARA = Project

Something with an end — DFAI 1.0, Move house. Status, the area it's part of, a due date, a summary.

PARA = Area

A responsibility with no end date — Garden, Health, a team. Projects and notes are filed under it just as under a project.

PARA = Resource

Reference worth keeping — an article, a manual, a how-to — kept as a project note of its own.

PARA = Archive

Done or no longer needed. Out of the way where it stands, never deleted, and back the moment PARA is set back.

Set where a project stands

  • A new project shows PARA = Project. Make it from the type's New or a picker's New project…. A project note with no PARA at all, or one DFAI can't read, counts as a project.
  • Change PARA in the note's properties to Area or Resource, and it moves to the Areas or Resources group in every picker. Its type stays Project, its file stays where it is, and links to it keep working.
  • PARA = Archive puts it away — out of the type's views, pickers and the sidebar's Project count, and out of the weekly review. Set it back to Project (or Area, or Resource) and it's back. Archive does the same from anywhere, keeping what PARA was; Unarchive gives that back. See Archive.
  • Area on a project links the area it's part of; its picker lists only areas. It's optional — a project saves without one.

Every note can be filed

  • A Project property on a task or a meeting links a project or an area. Its picker suggests both, each marked Projects or Areas, and offers Create project ‘…’ and Create area ‘…’ for a name no note has — Create area makes a project note with PARA = Area. A resource or an archived one is never offered, and nor is a person, a company or any other note.
  • A note with no type can be filed too: processing it gives it project all the same.
  • Linking the wrong kind of note — a person in a task's Project, typed by hand — shows “Project links to a project or area, not a person” under the property. A link to a note not written yet, or to one with no type, is left alone.
  • Any relation can point at several types this way: in the type's file write target: [project, area]. Edit type shows the first under Points at and the others under And at; switching Allow many keeps them, while choosing another type in Points at points it at that one alone.
  • project, area and resource in a relation's target are PARA values: they point at project notes whose PARA says that. target: [project, area, resource] lists all three groups; target: area, as Project's own Area has, lists only areas.

The types are set up for you

  • PARA is one type, Project. A vault without one isn't given it on its own: it hasn't taken PARA up, so it's offered instead (below). DFAI no longer writes Area or Resource types.
  • A Project type written before PARA was a property is offered it: “Project gains Area, linking area notes. Project gains PARA.” — each only if your type has no property of that name. A property you added to Project stays exactly as you wrote it.
  • DFAI's own types gain what DFAI ships on them. Opening a vault adds the keys DFAI ships to its built-in Meeting, Proposal, Decision, Daily and Block types when a file written earlier lacks them — a Meeting from before Tasks and Decisions, say, which would otherwise refuse to link an action item. Each type changed is a line in Activity, and a record is kept in .atlas/migrations/type-properties.md. A key you already have is never touched — the new keys are lines added after your own, and every line you wrote stays exactly as it was — and one you remove later stays removed. A type DFAI can't add to that way — its properties written as a list, or on one line as {…}, or two files that both say they are the Meeting type (a sync's conflict copy) — is left alone, with a warning in Activity saying why; merge the two files and the next open adds the keys. Project and Task keys are never added on their own: they stay an offer (below).
  • Anything more is offered, not done. On the Inbox page a box lists it — “Adds the Project type.” for a vault without one, “Task gains Project, linking project or area notes.” for a Task type with no project yet, “Meeting's Project will link project or area notes.” for one that links projects only. Add to the types makes those changes against the type files as they are at that moment — an edit you made while the box waited is kept — and keeps everything else in each file byte for byte; Not now puts the box away until the vault is opened again.
  • The Inbox's own types are offered the same way. A vault without them is offered “Adds the Proposal, Decision and Daily types.” — proposals are notes of the first two, and today's note of Daily. Nothing is written until you press Add to the types. (A Meeting type missing what the meeting import writes isn't offered it: DFAI adds those keys itself, above.) A Person or Company type without a Misheard as is offered one — “Person gains Misheard as.” — so the properties panel shows a name's misheard spellings by name; corrections use them either way.
  • Project is built in: it can't be deleted, and its properties are yours to change. Area and Resource types you already have aren't built in any more — delete them once their notes have moved.

Move Area and Resource notes onto the Project type

A vault from before PARA was a property has notes of the Area and Resource types. The Inbox page offers to move them: “Projects, areas and resources are one Project type now, with a PARA property. 12 notes would move onto it.”

  1. Press Preview the move. It lists every note that would move and what it becomes — Garden: Area → Project, PARA Area — what the Project type gains, if anything, and every note it leaves as it is, with why.
  2. Press Move 12 notes, or Cancel. Not now puts the offer away until the vault is opened again.
  • Each Area note becomes type: project with para: area, each Resource note para: resource. A project, area or resource whose file is already in Archive/ gets para: archive, and para_before_archive keeps what it was — area, resource or project — so Unarchive gives it back. It stays where it is.
  • Only type, para and, for an archived note, para_before_archive are written. No file moves, every other property and every line of text stays byte for byte, and a property you added is never removed.
  • A note that already has a para of its own — not Project, Area, Resource or Archive, like Life admin or a map — is left as it is, type and all, and the preview says so: Garden: its PARA “Life admin” is not Project, Area, Resource or Archive, so it is left as it is.
  • What the preview shows is what is written. A note open with unsaved typing, or changed since the preview read it, is left as it was — It changed since the preview read it. — and the run says so in Activity, one line for the move and one for each note left. Run it again later and it moves what's left; with nothing left the offer isn't shown. A note already archived by its PARA is never offered again.
  • Your Area and Resource type files stay until you delete them.

Capture goes to the Inbox

  • Quick capture ⇧⌘N — or ⌃⌥N from any app — makes its task in the Inbox folder at the top of the vault — made the first time it's needed — whatever note you're on. Once your tasks follow GTD, it starts with the status Inbox, whatever the Task template says.
  • Meetings arrive in their month, Meetings/2026/10/, and wait in the Inbox list from there. Anything you drop into Inbox yourself waits there too, of any type or none.

Process the Inbox

The Inbox is one list: every note in the Inbox folder, every imported meeting not yet filed under a project or an area (nor archived) wherever it lives, and every task whose status is still Inbox wherever it lives — one imported into Tasks/, say, or made by accepting a proposal. A task outside the folder with no status at all waits here too.

  1. Click Inbox at the top of the sidebar, or find it in search (⌘K). Its count is how many are waiting, and how many proposals wait for an answer; the weekly review counts the same. (The row shows once something is waiting, or when the vault has a view called Inbox.)
  2. The page lists everything waiting, newest first, with its kind and the folder it came in — Meeting · Meetings. Its heading says how many wait in all — 734 to process. It lists the newest 500 at a time: past that, the foot of the list says Showing the newest 500 of 734. and Show more lists the next 500, so every one can be reached. The page scrolls as a whole, so however many proposals are above it, each row keeps its controls whole. A meeting the import hasn't got to yet says Waiting to be imported; one it couldn't import says why, in red — Not imported: title is required. Click a name to open it.
  3. Clarify a task with one key. With a row focused — click it, or it takes the focus once the row above is done — the keys show on the row: N Next, W Waiting, S Someday, D Done (the task is archived; X does the same, as it does on Today), each written at once as one save you can undo. The row leaves the list as you press the key and the focus is on the next row straight away, while the save is written behind it, so five rows take five keys without waiting on the disk; a save that is refused brings its row back, saying why, and the rows you did after it are still saved. If you have already picked something on the row (a project, a date) and not saved it, a status key writes those picks together with the status — nothing you picked is left behind. T opens the Defer date and P the project picker (P shows only when there is a project or an area to file under). In the project picker a key opened, type a few letters and press Enter (or click a suggestion): the project is written at once, with anything else the row holds. Typing alone writes nothing. A date a key opened is held until you press Enter in it, since a date changes with every digit. Esc closes the suggestions; a second Esc drops what you picked and puts the focus back on the row. Longterm has no key; the status picker still offers it. The keys are live only while the row itself has the focus — inside a picker, a date, a dialog or search they are letters — never with ⌘, ⌃ or ⌥ held, never repeating while a key is held down, and not while a write is on its way. Clicking a key does the same.
  4. Or on its pickers. Pick its Status (the eight GTD statuses), a Project or area, and a Defer or Due day if it has one, then press Save — or Return in a date. Everything you picked is written in one save.
  5. File any other note — a meeting, a plain note — by typing a few letters in File under… and picking a project or an area; it is filed at once. The row leaves the list as you pick, and the filing is written behind it, so the next row is ready straight away; a filing that fails brings its row back, saying why. The project, area and Waiting on fields all suggest as you type, the way a relation does in Properties. A project or area no note has yet is offered as Create project ‘…’ or Create area ‘…’: it is made and the note filed under it.
  • Waiting offers who. Pick Waiting and a Waiting on… picker appears on the same row, listing your people. It's optional: press Save with or without someone. Pick a person and the status and the person are written together.
  • A status is enough. A task given any status but Inbox leaves the list, with or without a project — a single action needs none — and stays in the file it is in. (This holds once your tasks follow GTD; in a vault still on statuses of its own, everything in the Inbox folder waits until it is filed.)
  • A project files it — as a link. Filing writes project: "[[DFAI]]"; where the project's own note sits doesn't matter. A meeting in its month folder stays where it is. A note in the Inbox folder moves to its type's home folder for its day — a task to Tasks/2026/10/, a meeting from Inbox/Meetings to its month — and a plain note, or one whose type has no home, to Notes/2026/. It is never moved into the project's folder. Only the note's name goes with it, numbered if the folder has one by that name; nothing else in the file changes, and links to it are updated. A task that already lives outside the Inbox folder is linked to the project and stays where it is.
  • Only a project or an area still in use can be chosen — not one waiting in the Inbox itself, and not an archived one.
  • A refusal shows on the row it was for, in red, and what you picked stays picked. Nothing was written — except when the status was saved and the filing then failed: the row says so, and the task stays where it was with its new status.
  • Only statuses your Task type has. A vault whose tasks are still on statuses of their own is offered only the GTD statuses its Task type declares, and is never given one it doesn't; move the tasks to GTD to get all eight. A person picked while the row said Waiting isn't written if you change the status again before Save.
  • Undo. Once each one is saved, the box at the bottom right says Clarified “Call the bank”. with Undo: the note goes back where it was and says exactly what it said. Only the last one can be undone, and not once the note has been changed since — even by a save that landed a moment after the clarification. A clarification that leaves the note exactly as it was is not said, and has nothing to undo. One whose picks were written but that could not then be filed — its project taken away by sync meanwhile, say — still offers Undo, and its row says why it was not filed. The box goes by itself after 5 seconds, and the undo with it; it waits while the pointer is on it or Tab has reached its Undo. A checklist line's … is a task now. is said in the same box, with Open and Undo; only its refusal, with nothing to undo, stays on the note's page until you dismiss it.
  • Work down the list. Once a row is done — by a key or by Save — the next row has the focus, so the list is worked top to bottom from the keyboard; Tab walks its name, status, project and dates. J and K (or ↓ ↑) move to the row below or above without touching it, and the focused row is tinted. Return on the row opens its note. U (or ⌘Z) takes back the last clarification, as the box's Undo does, and the row it brings back has the focus again; while a clarification is still being written, U waits for it, so it never takes back the one before. Once the last row has gone, U still works: the page keeps the focus. The letters work with Caps Lock on. A strip above the rows lists the keys. A vault whose Task type lacks a status is not offered its key.
  • Make task, on a plain note with no type, makes it a task waiting in the Inbox, to clarify like any other.
  • Proposals aren't filed: they're answered, in the page's Proposals section, and are never in this list.
  • If your vault has a view called Inbox, the page's Open the Inbox view button opens it; it's still there under its own name. The view this repository's vault ships lists backlog tasks, everything under Inbox/ and any meeting that failed import.
  • Claude can do the same through atlas_clarify_inbox_item (a task) and atlas_process_inbox_item (filing).
