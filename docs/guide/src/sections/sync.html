Sync between Macs

Keep one vault the same on each of your Macs through a private GitHub repository. DFAI uses the GitHub login already on the Mac and never stores it.

Before you start (on each Mac)

  • In Terminal, run gh auth login, then gh auth setup-git. If they're missing, DFAI says so: “The GitHub command line isn’t logged in. In Terminal, run `gh auth login`, then try again.” (No gh at all: brew install gh first.)
  • The vault must not sit inside another git repository — such as the DFAI code folder. DFAI refuses: “This vault is inside another git repository (…), so DFAI won’t sync it: its notes would be mixed into that project. Move the vault out of that folder first.”

Set it up

  • Open the vault you want to sync, then Settings (⌘,) → Sync. Then one of: Your GitHub repositories — Search by name or owner, then Connect; Or create a new private repository — type a name, Set up sync with GitHub; Or paste an address — Connect existing repo.
  • Whichever you pick, the vault you have open becomes the repository, right where it is. DFAI never makes a subfolder for it, never copies it anywhere and never switches to another vault.
  • Made the repository yourself, say on github.com? Don't create another — use Connect existing repo (or Connect in the list) with its address.
  • The Mac asks first, in an DFAI sync dialog: “Connect this vault to …?” → Connect. Sync follows the repository's default branch, whatever it's called.
  • A repository that already has files is merged with the vault, not swapped for it — nothing is replaced. If both have DFAI settings and they differ, this vault's settings stay in force on the first connect. When all GitHub's version does is add settings this vault lacks, they are added to it and no copy is made; otherwise GitHub's copy is kept under Sync conflicts/atlas/ (for example Sync conflicts/atlas/settings (conflict from Studio).md) for you to take what you want from — see When both Macs changed a file below.
  • Sync counts as set up only once the repository exists and the vault has been pushed to it; then Settings → Sync says “Sync set up: this vault now syncs with its GitHub repository.” If creating it fails, the vault stays not set up — fix what the message says and try again; what DFAI already wrote (a .gitignore, a first commit) is reused.

When set-up is refused

  • The vault already sends somewhere else (an Obsidian Git vault, say) and you chose a new repository: “This vault already sends to …, so DFAI won’t make a new repository for it. To sync with that one, use Connect existing repo with its address. To use a new one instead, remove the old origin first: in Terminal, in the vault’s folder, run `git remote remove origin`.”
  • The name really is taken on your GitHub account: “You already have a repository with that name on GitHub. Pick another name, or connect that one by its address.” You only see this when it's true — any other failure says what actually went wrong.
  • A merge is half done in the vault's folder: “The vault’s repository is in the middle of a merge. Finish it, then set up sync.”

On your other Mac

  • Click the vault's name at the top of the sidebar → Open a vault from GitHub…. Paste the address, then Choose folder…; DFAI copies the vault into that folder and opens the copy.
  • This is for getting a vault you don't have open — never for syncing the one you do (that's Settings → Sync). Pick the open vault, or a folder inside it, and it's refused: “That folder is inside …, the vault you have open, so the copy would land inside it and DFAI would open the copy instead of your notes. To sync this vault with a GitHub repository, use Settings → Sync and connect it there. To open a vault from GitHub, choose a folder outside this one.” (Picking the vault itself starts “… is the vault you have open”; a shortcut or symlink to it is caught too.)
  • An empty repository is refused before anything is copied: “This repository is empty — there’s no vault in it to open. To put the vault you have open in it, use Settings → Sync and connect it there.”

While you work

  • Your changes are sent about 30 seconds after you stop — typing, an accepted Claude edit, an automation run, a move — and at least every 5 minutes while you keep working.
  • Every minute DFAI checks for other Macs' changes and brings them in; while you're typing, it waits until you stop. Unsaved typing is never overwritten; an open note reloads as after an outside edit.
  • Adjust both in Settings → Sync: When to send changes and How often to look for other Macs’ changes. Pause sync on this Mac stops it here only; Sync now syncs at once, paused or not.
  • A light at the bottom of the sidebar shows how it stands: Synced, Syncing…, N changes to bring in, N conflicts, Sync failed or Sync paused. Click it for Settings → Sync.
  • Closing the window syncs once more (waiting up to 20 seconds); anything left goes next time the vault opens.

What syncs

  • Everything in the vault: notes, pictures, .atlas (types, views, dashboards, templates, sources, automations and their logs, settings) and Chats/.
  • Not: secrets (each Mac's Keychain — set them on each Mac), the index (.atlas-cache/, rebuilt on each Mac), the Activity log, and window state.
  • Left out with a warning, and listed in Settings → Sync under Staying on this Mac, not synced:
    • a file of about 95 MB or more — “… is over GitHub’s 100 MB limit, so it isn’t synced. It stays on this Mac; to share it, make it smaller or keep it outside the vault.”
    • a folder that is a git repository of its own — “… is a git repository of its own, so only that folder isn’t synced: it stays on this Mac, and the rest of the vault still syncs. If it doesn’t belong in the vault, move it out.”
    • anything of .atlas that a line in your own .gitignore keeps out — “… is left out by a line in this vault’s .gitignore, so it isn’t synced and other Macs won’t get it. DFAI leaves your .gitignore as you wrote it; to sync it, remove that line.” DFAI never edits your lines; removing it is up to you.

When both Macs changed a file

  • Your version stays in place. The other Mac's is saved beside it as <name> (conflict from <Mac>).md; one of DFAI's own files (under .atlas) goes to Sync conflicts/atlas/ instead, so it isn't read as a second live rule or view.
  • Settings → Sync says “Both Macs changed a file. This Mac’s version was kept; the other Mac’s is saved beside it.”, and Activity gets a warning line. Nothing is lost, and git's conflict markers never land in a note.
  • DFAI's own files are merged first when they can be. For a markdown file under .atlas — a type, a view, the settings, or the record of the properties DFAI added to its built-in types — DFAI keeps one Mac's file exactly as it is and adds what the other Mac added: a new setting, or a new entry in a map such as a type's properties, copied line for line with its comments. So two Macs that each opened the vault, or ran different versions of DFAI, never leave a copy of a file DFAI wrote by itself. No copy, no warning.
  • This works when at least one of the two Macs did nothing but add: its additions go into the other Mac's file, and whatever else that Mac changed — a property removed, a label reworded — stands. A copy is still made, as above, when both Macs gave a setting different values or added the same one written differently; when neither Mac only added (each also removed, reworded, reordered, restyled or commented something, or added a blank line); when both changed the text under the settings; when the settings are a list or a single value rather than named keys, use YAML anchors (&name, *name), or have Windows (CRLF) line endings; when comments or blank lines follow the last setting, or a --- line was changed; and for the record of added properties, when you wrote anything in it — beside its list of keys or inside it, a field of your own — or took a key off it.
  • An old copy that adds nothing is cleared. Each sync, after bringing in the other Mac's changes, looks at every copy in Sync conflicts/atlas/ and merges it into its live file the same way. When that leaves the live file exactly as it is — every setting and property the copy has is already there, written the same, and nothing else in it differs — and all the live file has beyond the copy is properties DFAI added to a type itself (as .atlas/migrations/type-properties.md records), the copy goes to the Trash, the sync sends its removal to your other Macs, and Activity says “Cleared the conflict copy Sync conflicts/atlas/types/meeting (conflict from Laptop).md: .atlas/types/meeting.md already holds everything in it. It is in the Trash.” A copy that differs in anything — a value, a setting the live file lacks, even a space or the order of its lines — stays for you. So does one that lacks something DFAI didn't add — a property you took off on the other Mac, say, which the copy is the only sign of — and one either file of which can't be read, a copy of a copy, one that changes while DFAI checks it (Activity says so once), and one the sync has only just made. If the Trash won't take a copy, Activity warns you once, and again only if the copy changes.
Automations run on one Mac. Automations — scheduled, or set off by a note — run on one Mac only, so two Macs never run the same rule. The first Mac to set up sync gets them; a second Mac connecting later — even through Connect existing repo — leaves them where they are. To move them, turn on Run automations on this Mac in Settings → Sync on the Mac you want.
No tokens. DFAI never stores a GitHub token. An address with one in it is refused: “That address has a password or token in it. Use the plain address from GitHub’s Code button: this Mac’s own GitHub login is what signs in.”
