# DFAI local API, v1

DFAI answers HTTP on `127.0.0.1` while it is running and the API is turned on
in **Settings → Connections**. The types are in
`packages/application/src/api/contract.ts`; why it is shaped this way is
ADR-0016.

## Connecting

Settings shows the port and the token, and writes both to the connection file:

```
~/Library/Application Support/<bundle id>/api.json
{ "port": 27183, "token": "…64 hex…", "version": 1, "enabled": true }
```

The file is owner-only (mode 0600). `enabled: false` means the API is off and
nothing is listening; `port` is 0 until it has been on once. Read the file
again when a request is refused `401`: the token changes when it is rotated in
Settings, when the file was found readable by other users, and when the
recorded port was taken by something else as the API came on, at launch or in
Settings (DFAI then listens on another port too). Turning the API off and
straight back on keeps the port and the token.
Connect to `127.0.0.1` literally, never `localhost`.

Every request carries the token:

```sh
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:$PORT/v1/status
```

`/v1/status` says which DFAI is answering: `version` is the app's semver
version, and `build` the short SHA of the commit it was built from, or `null`
when the build did not know it. The MCP server reports the same version as its
own.

Refused before DFAI looks at it: no or wrong token (`401 unauthorized`), a
browser `Origin`, a foreign `Host` or a request target that names a host, as in
`GET http://127.0.0.1:27183/v1/status` (`403 forbidden` — send the path only),
a body over 1 MiB (`413 too_large`). No answer in 30 s is `504 timeout`, which
is not a refusal: a write may already have landed, so read the note before
retrying. The host checks in that order — target and `Host`, then `Origin`, then the token,
then the size — so a browser page learns nothing about the token. A path
outside `/v1`, or a method other than `GET`/`POST`/`PUT`/`PATCH`/`DELETE`, is
`404 not_found_route`; a query that does not decode to UTF-8, or a body that
is not JSON, is `400 invalid`. When the app has no window to answer, the reply
is `500 internal` at once, and so it is while DFAI is starting or its window
is reloading, with the message "DFAI is still starting — try again in a
moment": retry after a short pause. Every one of these refusals carries
`Connection: close` and the connection is closed after it: a pipelined request
behind a refused one is never answered, so reconnect to try again. A refusal
sent before the body was read is still delivered whole: the server reads and
discards up to 64 KiB of the unread body, for up to a second, before closing.

At most 32 connections are open at a time; more wait until one closes. A
connection takes no new request after 60 s (one in flight still finishes), so
a keep-alive client should expect to reconnect.

**From a Docker container** (n8n, say): `127.0.0.1` inside the container is
the container. Send to `http://host.docker.internal:<port>/v1/…` and set the
header `Host: 127.0.0.1:<port>` yourself — the `Host` check refuses
`host.docker.internal`, which is what it is there to do. The port and token
are the connection file's; when DFAI moves port or the token is rotated, the
container's copy must be changed too.

## Errors

```json
{ "error": { "code": "conflict", "message": "Tasks/Call Sam.md changed since you read it" } }
```

Branch on `code`, never on `message`. Codes and statuses: `invalid` 400,
`unauthorized` 401, `forbidden` 403, `not_found` / `not_found_route` 404,
`conflict` / `unsaved_in_app` / `exists` 409, `too_large` 413, `query_failed`
422, `internal` 500, `no_vault` 503, `timeout` 504. A `conflict` that time
will clear carries `retryAfter`, in seconds, beside `code` and `message`; a
DFAI query that does not read carries `at`, where in its text (see DFAI
queries); a dashboard or view spec its checker refuses carries `problems`,
`[{ at, message }]`, each where it is and in the checker's words (see the
assistant's drafts).

## Paths

A note is named by its vault-relative path, with `.md`, percent-encoded as a
single segment: `Tasks/Call Sam.md` is `/v1/notes/Tasks%2FCall%20Sam.md`. Paths
that climb out of the vault, are absolute, or point into `.atlas` are `invalid`.
A path finds its note whatever its case or Unicode normalization, as the Mac's
disk does, and answers carry the note's path as the vault spells it. So do a
view's path in `/v1/views/{path}/run` and the `folder` of `POST /v1/notes`:
`folder: "tasks"` makes the note in the vault's `Tasks/`, and the answer says
`Tasks/…`.

`POST /v1/notes` creates only in a folder that already exists; a missing
`folder` is `404 not_found`, naming it. With no `name` the note is `Untitled`,
numbered past any taken — even one taken while the note was being made, so
several made at once each get their own number. If every number it tries is
taken meanwhile (it gives up after 20), it is `409 conflict`, and retrying is
safe.

A request is for the vault open when it arrived. If another vault is opened
before it finishes, it is `503 no_vault` — including after a create or a write
has landed, when reading the note back would read the other vault.

## Writing safely

Every note carries `modified`. Pass it back as `ifModified` and the write is
refused with `conflict` if the note changed in between.

- `PATCH .../properties` and `POST .../append` take it optionally.
- `PUT .../body` requires it — there is no blind overwrite.
- A note open in DFAI **with unsaved edits** refuses body writes with
  `unsaved_in_app`. Property writes go through the open pane, as a board drag
  does, so they never clobber it. One sent while that pane is still opening the
  note is `conflict` with nothing written; retrying is safe.

Rows are `{ columns, rows, truncated, sql }`. `truncated` is true when more rows
matched than came back: for a query or a view, its `limit` or the host's row cap
cut it short; for SQL, the row cap (5000 rows). A query or view never lists
notes in `.atlas` or a hidden folder, and a page is filled to its `limit` when
enough notes match.

`POST /v1/notes` with no `folder` puts a note whose type has a home folder
there (ADR-0038: a task in `Tasks/<YYYY>/<MM>/`, made if missing), and any
other note at the root.

**Every list of notes is paged and capped** (#214): `GET /v1/notes`,
`GET /v1/notes/{path}/backlinks` and `GET /v1/tags/{tag}/notes` answer at
most `limit` notes (1 to 500, 100 unless said; more is `invalid`), with
`total`, how many match over every page, and `next`, a cursor to pass as
`cursor` for the next page, null on the last. The other lists — the Inbox,
meetings, the Archive, search, queries and views — are capped the same way
by their own `limit`. A caller never reads a folder of thousands in one
answer; search and the list by type or day are answered by the index.

`GET /v1/notes?date=2026-10-14` lists the notes about that day: those whose
file name starts with it (a daily note, a meeting filed as
`2026-10-14 Standup.md`) and those whose `date` property is that day. A
`date` that is not a real day written `YYYY-MM-DD` is `invalid`.
`GET /v1/notes/{path}` for a note that is not there is `404 not_found`, and
its message names up to five notes with a name like it, the same name in
another folder first.

`/v1/sql` reads the index: `files(path, title, summary, modified, size, progress)`,
`props(path, key, idx, value_text, value_num, value_date, value_json)`,
`links(src, dst, target, kind, leaf)`, `checks(path, idx, done, text)`,
`highlights(path, idx, id, kind, quote, comment, mark, color, anchor)` (a literature
note's highlights, ADR-0043), the FTS5 table
`fts(path, title, body)`, and a view `v_<type>` per type. `sqlite_master` has
the exact definitions.

`/v1/capture` makes the task in `Inbox/` — made if the vault has none — as the
app's capture does, numbered if the name is taken (P30-01). In a vault whose
Task type has the `inbox` status, the task starts there: `status: inbox`,
whatever the Task template says (P30-02).

### Tasks follow GTD (P30-02)

A task's `status` is one of eight, in this order: `inbox`, `backlog`,
`next-action`, `in-progress`, `waiting`, `someday`, `longterm`, `archive`
(ADR-0029). Every write that changes or makes a task — `PATCH .../properties`,
a card moved with `POST /v1/views/{path}/move`, `POST /v1/notes`,
`POST /v1/views/{path}/notes`, `POST /v1/quick-add`, `POST /v1/capture` — is
held to the app's rules, judged on the note the request leaves (a `type`
changed in the same request counts):

- `waiting` is a status like any other: it never needs `waiting_on` (#202).
  Who a task waits on — a link to a Person, or a plain name — is optional.
- `archive` is finished: the task is given `completed: <today>` unless the
  request or the note already says a day (an empty `completed` says none), and
  moving it out of `archive` takes `completed` away.
- A status is read as the index reads it: `"waiting "` or `["waiting"]` is
  Waiting, and is written back as `waiting`.

Moving a vault's tasks from older statuses to these eight is done in the app,
from the Inbox, never through the API: it rewrites every task, the Task type
and the views and automations that name a status, previewed first and undone
as one run.

### Timeblocks (P31-01)

A block is a note of type `block` (ADR-0030): `start` and `end`, each a day
and a time (`2026-10-12T09:00`), `tasks`, links to the tasks it holds, and
`gcal_event_id` and `gcal_etag` for the Google event it will sync with. Blocks
are made, read and changed through the notes routes like any other note. The
app writes the Block type into a vault once its tasks follow GTD; the API
never writes `.atlas/types`.

`POST /v1/query` with `"schedule": true`, on a query of `task`, adds a last
column, `schedule`, to each row: the task's
`{ estimate, scheduled, done, overBy }`, in minutes, as the task's page shows
them.

- **scheduled** sums the blocks linking the task. A block holding one task
  gives it all of its time; a block holding several shares its time by what
  each has left of its estimate — in proportion when they need the whole
  block, else each what it has left, and the rest in equal parts to the tasks
  with no estimate. Shares are whole minutes that add up to the block. Blocks
  that overlap each count, so the task reads as over-scheduled.
- A block's length is its wall-clock length as written, across midnight
  included; one without a time at both ends, or ending no later than it
  starts, gives nothing.
- **estimate** is null when the task has none; `2h` and `1h30m` are read as
  well as minutes, a day or a week is not. **done** is all of the estimate
  once the task holds the status ticking writes (`archive`), else 0, and null
  with no estimate. **overBy** is how far scheduled runs past the estimate.
- `schedule` on another type, or beside a `schedule` column, is `invalid`. A
  schedule the index could not read whole is `query_failed`, never a short
  answer.

`POST /v1/tasks/schedule` (P31-02) sets time aside for a task as dragging it
onto the calendar's empty time does in the app, by the same code: a new block
from `start` for `minutes`, linking the task, made from the Block template when
the vault has one, at the top of the vault, named `<task> block` — numbered
when taken, so calling it again for the same task splits it across another
block. It answers 201 with the block.

- `task` is the path of a note of type `task`; any other note is `invalid`,
  none is `not_found`.
- `start` is local wall-clock time to the minute, exactly `2026-10-12T09:00`.
  Anything else — no time, seconds, `Z`, an offset, words after it — is
  `invalid`, with why: a zone names another moment than the digits (an
  agent's `toISOString()` is UTC), and a block holds none, so the block would
  land hours away. Convert to the Mac's local clock first. A block running
  past midnight ends the next day, and its end is the clock's: two hours from
  01:30 is 03:30, whatever the clocks did that night.
- `minutes` is a whole number from 1 to 1440. Without it, the block is as long
  as the task still needs — its estimate less what its blocks already give it
  and what is done — or 30 when it has no estimate or needs nothing more, as
  the app sizes a dropped task. That read is `query_failed` when the index
  cannot answer it whole.
- Adding a task to a block that is already there is a change to the block's
  `tasks`, through `PATCH /v1/notes/{path}/properties`.

### Checklists (P30-03)

A note's `- [ ]` and `- [x]` lines are its checklist — a task's subtasks.

- **Progress.** How far through its checklist a note is, as a whole
  percentage rounded down (2 of 5 ticked is `40`; `100` only when every box
  is), or `null` with no box. Rows from `POST /v1/query` and
  `POST /v1/views/{path}/run` carry it as a `progress` column for every type
  that does not declare a `progress` property of its own (then the column is
  the type's). In a DFAI query it is the field `progress`, compared as a
  number (`WHERE progress >= 50`, `SORT BY progress DESC`), also through a
  relation (`project.progress`). In SQL it is `files.progress`, and each box
  is a row of `checks`, `idx` counting from 0 in the order written.
- **`POST /v1/notes/{path}/promote`** makes one line a task of its own, as
  "Make task" does in the app. Name the line by `text`: either its words as
  DFAI shows them, without the box (`Ring Mara Quill`), or its markdown as
  the note's writer writes it — the note's own spelling for links, tags and
  code, `**` for bold (`Ring [[Mara Quill]]`). When two lines say the same,
  `line` says which — its place among the note's boxes, from 0, nested lines
  after the line they are under. The task is made beside the note, named by
  the words (cut by whole characters to fit a file name), with `type: task`,
  `status: inbox` (`archive` and today's `completed` for a ticked line; no
  status in a vault whose Task type is not GTD's), `source` a link to the
  line (`"[[Plan#^k3x9q1]]"`, the line given that id if it has none) and
  `project` whatever the note is filed under — or the note, when it is a
  project or an area.
- **Nothing the line said is lost.** A line of plain words becomes the link
  alone, showing the same words (`[[Order chairs]]`, or `[[Task name|the
words]]` when the name had to differ). A line holding anything more — a
  link, a tag, code, emphasis, or a character markdown reads (`[ ] | # ^ \`
  `` ` `` `< > * _ ~ & !`) — keeps all of it after the link, and its markdown
  is also the task's body, so its links and tags reach the task. The line
  keeps its box, its id and the lines nested under it. The list holding the
  line is written again, so a list written with `*` or `+`, or numbered, is
  written with `-` — the editor's checklist has one spelling (ADR-0003); the
  rest of the note keeps its bytes.
- Both writes go through the app's own (`createNote`, `saveNote`), so the
  task rules hold. Refused, writing nothing: `not_found` when no line says
  `text`; `exists` when the line is a task already — it starts with a link to
  a task note, as a promoted line does — so a retried request never makes a
  second task; `invalid` for an empty `text`, or two lines saying it and no
  `line` naming one of them; `unsaved_in_app` when the note is open in DFAI
  with unsaved typing; `conflict` when it changed while the task was being
  made — the task that request made is then taken back to the Trash, so
  nothing is left half done.

### The Archive

Archiving is the app's Archive command, for up to 100 notes at once — and the
one move the API makes (ADR-0016). Each note moves under `Archive/` at the path
it had — `Projects/X.md` becomes `Archive/Projects/X.md`, numbered if that is
taken — and gets `archived: <today>` and `archivedFrom: <where it was>` in its
frontmatter; the rest of the file is kept byte for byte. If the note already
had keys of those names (or `archivedPrior`), their text is kept under
`archivedPrior` and given back exactly as it was written. A note too many
folders deep for DFAI to read it once it is under `Archive/` is refused.

`POST /v1/unarchive` puts each note back at its path without `Archive/` —
`Archive/Projects/X.md` goes to `Projects/X.md` — numbered if something has
taken it since, and takes the stamp off. `archivedFrom` is only used to spell
that same place as the note had it (another case, or without the number
archiving gave a clashing name): editing it, through `PATCH .../properties` or
anything else, never sends a note to another folder, another name or another
extension. Moves happen only in user space and never overwrite anything, and
`moves` names each folder as the vault spells it.

**The API never saves someone's typing.** A note open in DFAI with unsaved
typing is not moved, and a note linking to one that moved that has unsaved
typing is not rewritten: each is listed in `failed` with
`code: "unsaved_in_app"`. A pane holding a note that moved follows it to where
it went. Links in other notes that would stop opening a moved note are
rewritten once the batch has moved, and `linksUpdated` counts them.

A batch never fails as a whole for one note. `failed` lists each path that did
not move, with a `reason` for people: a path in `.atlas` or a hidden folder
(`node_modules` in any case among them), a file that is not a `.md` note, a
note that is already archived (or, to unarchive, is not), and a path with no
note. A note that moved but whose frontmatter could not be updated — its YAML
cannot be read, say — is listed under where it went, and so is each linking
note whose links could not be rewritten. A path finds its note whatever its
case. A vault switched mid-batch still answers what moved before the switch.

`GET /v1/archive` lists archived notes, most recently archived first, as
`{ path, title, from, archivedOn }` — `from` is where unarchiving puts it back,
and `archivedOn` is `YYYY-MM-DD`, or null for a note filed there by hand.
`search` keeps notes whose title or path holds every word, of its first 16. An
index that cannot run the listing is `query_failed`. `limit` is 1 to 500
(default 50); `next` is the `offset` for the next page, or null.

Search, saved views and queries leave archived notes out, as the app does,
unless `includeArchived` is true — `?includeArchived=true` on search, where each
archived hit then carries `archived: true`, and `{ "includeArchived": true }`
in the body of a run or a query. A dashboard's widgets and a calendar never
list them.

A view saved as a DFAI query (`query:`, ADR-0019) runs its query as the app
does: checked against the vault's types, its links resolved against the
vault's notes. Its text says whether archived notes are listed
(`INCLUDE ARCHIVED`), so `includeArchived` does not apply to it. A query that
does not read, or names something the vault lacks, is `invalid`, with the
problem as the app shows it. A dashboard's query widgets run the same way.

### The Inbox

Everything captured waits in the `Inbox` folder at the root of the vault —
tasks from `/v1/capture` and the app's capture — until it is processed
(P30-01). An imported meeting waits wherever it lives — its month's folder,
`Meetings/2026/10/` — until it is filed under a project (ADR-0038). Proposals wait there
too, as notes of type `proposal`, but they are answered through the proposals
routes and never filed.

`GET /v1/inbox` lists what waits to be filed, as the Inbox page does: newest
first, `{ items: [{ path, title, type, arrivedIn, importOutcome, importError,
task }], truncated, next, total }`, a page of `limit` (1 to 500, 500 unless
said) at a time (#167). `total` is how many wait in all; while `next` is not
null, pass it as `cursor` for the next page. The cursor marks the last note
listed — when it last changed and its path, the list's order — so filing or
editing what one page listed before asking for the next skips and repeats
nothing. It is one Inbox (#112): every note in `Inbox/`,
every task whose `status` is `inbox` wherever it lives — imported into
`Tasks/`, say — and every meeting the import brought in (it declares
`atlas_import`, and the import stamped it or it is arriving in its month)
with no `project` yet, wherever it lives (#214). Once the vault's Task type has the `inbox` status, a task given
another GTD status has left the list, with or without a project, and a task
outside `Inbox/` with no status at all waits like a new one. `task` is null
for a note that is not a task, else what it already says: `{ status, project,
waitingOn, waitingOnNames, defer, due }`, where `project` and `waitingOn` are
paths. `arrivedIn` is the folder of the Inbox it came in (`Meetings`, or
`''` for anything outside the Inbox folder); `importOutcome` is what the meeting import made of a meeting file
(`imported`, `duplicate`, `error` with `importError`, or `pending`), null for
any other note. Notes of type `proposal` are not listed, wherever they are; a
plain note in `Inbox/Proposals/` is.

`POST /v1/inbox/clarify` is GTD's clarify step for one item, as a row of the
Inbox page does it. Everything the body names is written in **one**
byte-preserving save of the note, held to the task rules (ADR-0029): `status`
(one of the eight), `waitingOn` (the path of a note of type `person`),
`defer` and `due` (`YYYY-MM-DD`), `contexts`. A key left out is left as the
note has it; `null` clears `waitingOn`, `defer` or `due`, and `[]` clears
`contexts`. `waiting` never needs a person (#202); `waitingOn` is optional.
Anything refused is `invalid`: a status that is not one of the eight, a
person who is not one, a body that chooses nothing. A refusal writes nothing. `project` files a note that is in `Inbox/`
exactly as `/v1/inbox/process` does, after the save; a task or a meeting that
lives elsewhere is only linked to it, in the same save, and stays where it is. Only
a task takes a status, a wait or a date; `asTask: true` first makes a note
with no type a task. A proposal is refused. The answer is `{ path, movedFrom,
failed, linksUpdated }`: where the note is now, where it was if it was filed,
and — once its properties are written — anything of the filing that could not
be done. A note open in DFAI with unsaved typing is `unsaved_in_app` and is
left alone; one that changed on disk between being read and written is
`conflict`. Undo is the app's; the API has none.

The route decides on **any task the API reaches**, not only one `GET
/v1/inbox` lists, so an agent can move a task on from anywhere. It never
decides on an archived note, never makes a note that already has a type a
task, and never writes a status the vault's Task type does not declare (a
vault with no Task type is taken to follow GTD). `waitingOn` is written only
when the task is, or is being made, `waiting`; leaving `waiting` keeps who it
waited on, as every other write of a task does.

`POST /v1/inbox/process` is the Inbox's **Process**, for up to 100 notes at
once: each is filed under `project` — given `project: "[[…]]"` linking it
(ADR-0038). Filing is the link, never the project's folder. A meeting waiting
outside the `Inbox` folder, in its month, stays where it is and is listed in
`linked`. A note in the `Inbox` folder moves to its type's home folder for its
day — `Inbox/Call Sam.md` (a task) lands as `Tasks/2026/10/Call Sam.md`,
`Inbox/Meetings/2026-09-29 Sync.md` as `Meetings/2026/09/2026-09-29 Sync.md` —
and a plain note, or one whose type has no home, goes to `Notes/<year>/`, by
its own name, numbered if that is taken. The rest of the file is kept byte
for byte; a `project:` the note had is replaced. The answer is the Archive's,
`{ moves, failed, linksUpdated }`, with `linked`: the paths filed in place.

`project` is the path of a project or an area — a note whose `type:` is
`project` or `area` — that is still in use: not waiting in the Inbox itself,
not archived, and not in `.atlas`. Where its own note is kept no longer
matters, since nothing moves into its folder. Anything else refuses the whole
request with `invalid` before a note moves, as does a path with no note.
A proposal among the paths is listed in `failed` — "A proposal is answered,
not filed" — and left where it is.

Each note follows the Archive's terms below: it must be a `.md` note in the
Inbox folder or a meeting (any other note elsewhere is listed in `failed`, and
the rest carry on); it never
lands over anything; a note open in DFAI with unsaved typing is left where it
is with `code: "unsaved_in_app"`; links that would stop opening a moved note
are rewritten and counted in `linksUpdated`.

### The weekly review

`GET /v1/review/weekly` answers the app's Weekly review page (P30-07), read
from the index on the app's clock, and writes nothing. `review` holds:

- `staleWaiting` — tasks Waiting and untouched for more than 7 days, the
  longest untouched first, each with `waitingOn`: who `waiting_on` names, a
  link by what it shows and a plain name as written, joined with ", ".
- `projectsWithoutNextAction` — projects whose `status` is `active` with no
  task in use filed under them (by `project`) that is Next Action or In
  Progress. That is asked of the index for each project, so it holds even
  when `truncated` is true.
- `overdue` — tasks due before today that are still open: Inbox, Backlog,
  Next Action, In Progress or Waiting. The earliest due first.
- `untouchedSomeday` — Someday and Longterm tasks untouched for more than 30
  days, the longest untouched first.
- `inbox` — `{ count, toFile, toAnswer, more }`: what waits in the one Inbox,
  as the sidebar counts it — `count` is the notes to file (`toFile`, as the
  Inbox page lists them) plus the proposals to answer (`toAnswer`, as
  `/v1/proposals` lists them); `more` when there are more notes than it counts
  (past 500).
- `today` and `truncated` — the day it was taken, and whether the index held
  tasks back (past 5000), so a task section may be missing items.

A task is `{ path, title, status, due, defer, recurrence, waitingOn, contexts,
project, projectTitle, modified }` — `recurrence` as the task's `recurrence`
says (null when it does not repeat), `contexts` as written, `projectTitle` the
linked project note's title — and a project `{ path, title, status }`. "Untouched" is the file's last change
(`modified`, in milliseconds): DFAI keeps no "waiting since", so any edit
counts as a look. A task deferred past today is in no section until its
`defer` day. Finished tasks (`archive`), and archived or hidden notes, are
never listed.

The page's quick actions are routes that already write: a task's status or
`defer` through `PATCH /v1/notes/{path}/properties` (held to the task rules —
Archive dates `completed`; Waiting never needs anyone), and a project into the
Archive through `POST /v1/archive`. The page defers a week from today, and
moves a late task only to Someday or Longterm, the statuses that take it off
`overdue`. One difference: the page's Archive finishes a task as ticking it
does, so a repeating task (one with `recurrence`) rolls on to its next `due`
and back to `next-action`; `PATCH` with `status: archive` finishes it, which
ends its series.

### The assistant: brief, open loops, what was said (P32-04)

Three read-only routes answer the questions James asks Claude most — "what do
I discuss with Larkspur Payroll today", "what did Tobias say about the
cut-over last week" — about one note named by `entity`, a vault path as
`/v1/notes` answers it (`People/Mara Quill.md`). Each reads the note's linked
page (P30-06) from the index — one bounded query a section, the page's 200
newest notes a section — plus one statement for every item's `source`, one to
check the blocks they cite and one for follow-ups; only the `entity` note, and for `meetings` the meetings it
quotes, are read from the vault. None writes, and none ever writes a block id.

- `GET /v1/assistant/brief?entity=&date=` — a Person, Company, Project, Area
  or Meeting note on a day (`YYYY-MM-DD`, today on the app's clock when left
  out). `brief` holds `entity`, `date`; `lastTouch`, the newest meeting dated
  on or before `date`, and `lastMeeting { meeting, tasks, decisions }`, every
  task joined to it (finished or not) and its decisions; `meetings` (5) and
  `decisions` (10), dated on or before the day, newest first; `openTasks`,
  `waitingFor`, `followUps` as `open-loops` answers them; `mentions` (10),
  other notes linked with it changed in the 30 days up to `date` (not from
  today: a brief for last month reads as of last month); `related`, the
  people, companies and projects its page names (`relation` says which);
  `truncated` and `problems`. Tasks are as they stand now: `date` says what
  had been met and decided by then, and what is `overdue` on it.
- `GET /v1/assistant/open-loops?entity=` — a Person, Company, Project or Area.
  `openLoops` holds `entity`, `date` (the day it was read, named as the
  brief names its day), `openTasks`, `waitingFor` (what it
  waits on — for a person, what they owe), `followUps` (open tasks tagged
  `#follow-up` linked with it or with any of its meetings: one made from a
  meeting is joined to it by the meeting's `tasks` and its own `source`, so a
  person's follow-ups are found though they never name the person). A meeting
  is shared by everyone in it, so a follow-up reached only through a meeting
  is kept when it names no Person (the owner's to chase) and left out when it
  names a Person other than `entity`; one that names `entity` is kept either
  way. Every follow-up says `via`: `direct` when it names the page, `meeting`
  when only a meeting reached it, with that `meeting` cited. A waiting
  follow-up keeps `waitingOn` and `waitingDays`,
  `truncated` and `problems`. A task is listed once: a waiting-for before a
  follow-up, a follow-up before an open task. At most 50 a list.
- `GET /v1/assistant/meetings?entity=&since=&until=&about=&limit=` — a Person,
  Company, Project or Area's meetings from `since` to `until` (`YYYY-MM-DD`;
  `until` is the app's today when left out, so a meeting still on the calendar
  is not one that was held; an undated meeting is left out once either is
  given), newest first, at most `limit` (10; 1–50). `meetingQuotes` holds
  `entity`, `since`, `until`, `about`, `speakers`, `meetings`, `truncated` and
  `problems`. A day is read as the calendar has it: `2999-02-30` is undated.
  Each is `{ path, title, date, cite, quotes, matched }`; a quote is
  `{ speaker, time, quote, cut, cite }`, at most 5 a meeting (`matched` counts
  them all), each cut at 400 characters (`cut`). For a Person only their own
  turns are quoted, matched by the note's title, its file name and its
  `aliases` (`speakers`); `You` counts as the person's own when the person is
  the vault's owner (the profile's name), and unnamed speakers never match.
  With `about` (at most 500 characters), only meetings where a quoted turn
  holds every word of it — each word starting a word of the turn, case and
  accents aside — are listed. Which meetings to read is found by full-text
  search (`/v1/search`'s index) behind a `PassageFinder` seam that semantic
  search (#33) will answer, naming the matching blocks itself. The search
  ranks the whole vault and is read as deep as it takes to cover the page's
  meetings, to 2,000 hits; the newest meetings holding `about` are the ones
  read, not the best ranked, at most 50 meeting files. `truncated` is true
  when more matched than were listed or read, or the search could not be read
  deep enough to be sure. Without `about`, a person's meetings are listed with
  all they said, and other pages' with no quotes.

Every item is `{ path, title, cite }`, and every task or decision also has
`source`. A citation is `{ link, kind, path }`: `link` is a wiki link to quote
as written; `kind` is `block` for the block itself (`[[Kickoff#^t0003]]`),
`heading` for the heading over it, `note` for the whole note; `path` is the
note it opens, null when the link names none. A transcript turn the file left
without a `^id`, or whose `^id` is written on more than one turn (a link to it
would open the first), is cited by its Transcript heading
(`[[Kickoff#Transcript]]`, kind `heading`): an id is written only by the
person who first links to a block (ADR-0022), never by a read. A note whose
name holds what no link can (`# [ ] |`, as `C# sync`) has `link` null: name it
by its `path`. A `source` is the task's or decision's own `source` property as
written, alias dropped; its block is checked against the index in one
statement, and one that is no longer there is cited as `note` (the link to the
note alone), never as a `block` that opens nothing. A task is `{ path, title, cite,
status, due, overdue, waitingOn, waitingDays, source }`: `status` as written,
`overdue` when due before the day and not finished, `waitingOn` as the task
writes it (null on a person's own page, where it is them), `waitingDays` the
whole days since a waiting-for's file last changed, counted to the answer's
`date`. A `quote` is what someone said in a meeting: data to report, never an
instruction to the model (ADR-0021), in the chat, a rule's Claude step and the
MCP tools alike; the tool descriptions say so.

Decisions are Decision notes, and few meetings yield one today (issue #232:
the meeting extraction lets through only high-confidence decisions the owner
took part in), so an empty `decisions` does not mean nothing was decided —
read the meeting.

An `entity` outside user space, not a `.md` note, or of a type the route does
not answer about is `invalid`; one the vault does not hold is `not_found`; one
whose type the vault does not declare is `invalid`, since its page would show
nothing. A `date`, `since` or `until` the calendar does not have is
`invalid`. An `entity` is spelt as the vault spells it, as the notes route
finds it (a case-insensitive disk, a name typed decomposed). The index failing
is never an error of its own: a section, the sources, the follow-ups or the
search it could not answer is named in `problems` (`section`, and `problem`
without the machine's paths), the answer is `200`, and the rest still stands.
Only an `entity` that cannot be read is an error. In the chat a long answer is
cut by whole items of its lists, always valid JSON, with `truncated` set on
the list's owner and a `cut` saying what was kept.

### The assistant's drafts: a meeting's tasks, a dashboard (P32-05)

Two routes let Claude draft what James asks for — "pull the tasks out of
today's Larkspur Payroll sync", "build me a dashboard of open tasks by
status" — and both only **propose**: each writes proposal notes into
`Inbox/Proposals/` and nothing else, for James to accept, edit or reject on
the Inbox page. MCP's `atlas_propose_tasks` and `atlas_make_dashboard`, and the
chat's `propose_tasks` and `make_dashboard`, are these routes. A rule's
Claude step has neither.

- `POST /v1/assistant/propose-tasks` `{ meeting }` — runs the meeting
  extraction (P29-05) on one meeting note now, with the provider and model
  Settings → Claude chose: the owner's own tasks (at Inbox), what they wait on
  from others (a task Waiting on that Person), decisions and follow-ups, each
  a proposal citing the transcript turn it came from. An item citing no turn
  of this meeting is left out and named in `dropped`. Answers
  `{ proposedTasks: { meeting, proposed: [path], alreadyProposed, unchanged,
dropped: [{ title, reason }], left: [{ path, reason }], warnings } }`. Each
  proposal keeps `meeting_digest`, a digest of which meeting it was drafted
  from (its provider and id, or its path when it has none) and that
  meeting's words (its body, not the frontmatter Accept writes tasks into).
  Asked again about the same meeting with words unchanged since, Claude is
  **not asked** — only proposal notes count, and another meeting with the
  same words is its own: the answer
  is `unchanged: true`, `proposed: []`, and `alreadyProposed` counting the
  proposals that draft made, open or answered. Once the words change, Claude
  is asked again, and still proposes nothing twice — the same item of the
  same meeting is the same proposal, whether this route or the meeting
  extraction rule made it (`alreadyProposed` counts them). A meeting none of
  whose items became proposals has nothing to remember it by, so asking
  again asks again. A meeting that takes longer
  than 25 seconds answers `202 { proposingTasks: { meeting, running: true } }`
  rather than outlast the host: the draft goes on, and its proposals follow in
  `/v1/proposals`. How it ended is said in the vault's Activity log — and,
  when it failed, as a notice in DFAI's window — naming the meeting and why.
  Right before its first write a draft checks that its vault is still the one
  open and that the meeting is still there and still the same meeting (by
  provider and id — not another written at its path meanwhile); if not, it writes nothing (`conflict`
  when that happens before the answer). `meeting` is a user-space `.md` note, spelt as the vault
  spells it; one the vault does not hold is `not_found`, one that is not a
  meeting `invalid`. It is `conflict` when DFAI cannot reach Claude yet, when
  Claude could not draft it (its answer did not read, the provider was not
  ready — the reason says which), or while the same meeting is being drafted.
  Each draft Claude makes costs what the chosen provider charges.
- `POST /v1/assistant/make-dashboard` `{ spec }` — checks a dashboard or a
  saved view and leaves it as a proposal. `spec` is `{ kind: "dashboard",
name, description?, widgets: [...] }`, each widget as a dashboard note's
  `widgets:` lists it (`{ kind, title?, type, groupBy?, filters?, span? }`, or
  `{ kind: "sql", sql, show }`, or `{ kind: "query", query }`), or `{ kind:
"view", name, type, layout }`. A dashboard is checked by the widget editor's
  own rules (`widgetProblems`, whose last word is the dashboard's parser)
  against the vault's types; a view by the New view dialog's. A spec either
  refuses is `400 invalid` with the problems in `problems`, `[{ at, message
}]` — `at` is the field or widget (`name`, `widgets[2]`), `message` the
  checker's words — and nothing is written. The body stays small whatever
  was sent: at most 50 problems (then one saying how many more), each cut at
  200 characters (cut by whole characters, never through an emoji), and
  `message` only counts them. The checker refuses rather
  than reads loosely: a `filters` that is not a list of `{ key, operator,
value }` with a known operator (a null value only with `isEmpty` or
  `isNotEmpty`), an unknown `show` or `icon`, a `span` or `limit` that is not
  a whole number in range, a `title` that is not text, a `highlight` that is
  neither text nor a number, and a name with nothing visible in it or holding
  an invisible character outside an emoji: a zero-width or bidirectional
  formatting character, a joiner that does not join two emoji, or Unicode tag
  characters outside a subdivision flag. One
  that passes answers `{ proposedSpec: { kind, title, proposal, problem } }`:
  `proposal` is the proposal note, or null with `problem` saying why — `{
message, proposal }`, the same spec proposed before and what became of it
  (`It is proposed already, waiting in the Inbox.`, `It was already accepted
on 2026-10-23.`) with that proposal's path, or a write that failed. Its
  Inbox card shows every widget as Accept will write it, filters, SQL
  statements and DFAI queries whole. What is written is only what the checker read: a widget's key
  the editor does not know is not carried, and nothing in a spec names a path.
  **Accepting it is the app's alone**: the Inbox's Accept writes the dashboard
  into `.atlas/dashboards` (a view into `.atlas/views`), numbered past a name
  already taken and checked again against the types as they are then; Undo
  takes it back. `POST /v1/proposals/{path}/accept` refuses a dashboard or view
  proposal with `403 forbidden`, writing nothing (ADR-0016's addendum for
  P32-05); rejecting one through the API is as for any proposal.

### Today

`GET /v1/today` answers the app's Today page (#111), read from the index on
the app's clock by the use-case the page runs, and writes nothing. `today`
holds:

- `sections` — always these six, in order, each `{ id, count, groups }`:
  - `overdue` — open tasks (Inbox, Backlog, Next Action, In Progress,
    Waiting) due before today, the earliest first.
  - `dueToday` — open tasks due today.
  - `backToday` — tasks whose `defer` is today, in any status but Archive
    (Someday and Longterm included), and Inbox, Backlog, Someday and Longterm
    tasks whose `defer` day has passed: no other section would list those, so one put off to a day the
    app was never opened still wakes up. Today's first, then the most
    recently passed.
  - `inProgress` — In Progress tasks.
  - `nextActions` — Next Action tasks, a group per project by title, those
    filed under no project last.
  - `waiting` — Waiting tasks, a group per `waitingOn`, nobody last; within
    a group the longest wait first.
- `stalledProjects` — how many active projects have no Next Action or In
  Progress task: the weekly review's `projectsWithoutNextAction`, counted.
- `inbox`, `today` and `truncated` — as the weekly review's.

A task is in one section only: the first, in that order, that claims it — an
In Progress task due yesterday is in `overdue` alone, so the counts add up to
the tasks listed. A task deferred past today is in none until its `defer`
day. A group is `{ key, label, project, tasks }`: `label` is the project's
title or the person's name, null for the tasks with neither and in the
sections that are not grouped (which hold one group, or none when empty);
`project` is the project's note. A task is the weekly review's, plus
`waitingDays`: for a Waiting task, the whole days (24 hours each) since its
file last changed — `modified`, not a recorded "waiting since", so any edit
restarts it — and null for any other status.

The page's actions are `PATCH /v1/notes/{path}/properties`: a `status`, or a
`defer` of tomorrow or a week on. Its tick finishes a task as the weekly
review's Archive does, with the same difference for a repeating task.

### Artifacts

`POST /v1/artifacts` saves a Claude artifact in one call: a note of type
`artifact` in `artifacts/` (made if the vault has none), named by `title` and
numbered if taken, and — when `html` is given — the page as `index.html` in a
folder beside it, `artifacts/<slug>/`, recorded on the note as `saved`. `kind`
is one of `page`, `deck`, `design`, `doc`, `other`, guessed from the page, then
the link, when left out. `url` must be `http` or `https`. `project` is the
project note's name.

**The 1 MiB body cap applies to the whole request.** A page larger than that,
and any other file the page uses, goes in chunks with
`PUT /v1/artifacts/{path}/files/{name}`, where `{path}` is the artifact note's
path and `{name}` the file's path inside its folder (`app.css`,
`img%2Flogo.png`), both encoded as one segment. Each chunk is `text` (written as
UTF-8) or `base64`; send ≤ 512 KiB of bytes per chunk. The first chunk has
`offset` 0 (the default) and creates the file — `exists` if it is already
there; each next one sends `offset` = the `size` the last answer gave, and is
refused with `conflict` if the file is not that long, so a retried or reordered
chunk never corrupts it. The first file makes the copy's folder and sets
`saved` and `saved_at` on the note. Only `html`, `htm`, `css`, `js`, `json`,
`svg`, `png`, `jpg`, `jpeg`, `webp` and `woff2` files, at most four folders
deep, 32 MB each, never hidden, never outside the artifact's folder, and never
`atlas-thumbnail.png` at its top, which is kept for the thumbnail.

Once the last file is in, `POST /v1/artifacts/{path}/thumbnail` pictures the
page's first screen (1280 × 800, as a 640 × 400 PNG) in a webview of its own
with no way back to DFAI, keeps it as `atlas-thumbnail.png` in the copy, and
sets the note's `cover` to it — unless the cover was set by hand to something
else, which is left alone. It answers with the note; `thumbnail_failed` (422)
says why when the page could not be pictured (only macOS can; a page that
never loads). The MCP tool `atlas_save_artifact` does all of this for you.

### Exporting a note for Confluence

`GET /v1/notes/{path}/export?format=confluence` answers the note as markdown
for a Confluence page (P32-07):
`{ export: { path, format, title, markdown, dropped } }`. `title` is the note's
title as its page shows it. In `markdown`:

- a wiki link is its words — its alias, or the linked note's title, then
  `› Heading` for a link to a heading (a link to a block is the note alone);
- a block shown in place (`![[Note#^id]]`, `![[Note#Heading]]`) is that block
  or section, quoted, under `*From <title>*`; one whose note or block is gone
  is `[Not found: …]`;
- a callout is a quote opening with its name in bold, then its title:
  `> **Warning:** Mind the gap`;
- a link or image the page cannot reach is its words (`[Image: alt]` for an
  image, `<img>` too); a reference link or image on the web is written in
  place, and every link definition is left off;
- a footnote of a shown block is relabelled after its note (`[^Sources-1]`),
  never sharing a label with another on the page;
- a link's words that look like an address carry an unseen word joiner, so the
  page does not make them a link;
- tasks, tables, code, headings and links and images on the web stay as they are.

The same rules hold in markdown the editor does not model (a block with a
footnote or inline HTML), read by the same parser. `dropped` lists everything
left out, by kind, in this order, each item as the note writes it, once:
`property` (frontmatter keys — or `(frontmatter that is not properties)` and
`(frontmatter DFAI cannot read)` for a block of anything else), `link`
(where a link went, its words kept), `embed` (`![[file]]` named instead of
shown), `missing-embed`, `image` (an image in the vault, which a page cannot
reach), `block-id`, `comment` (one never closed takes the rest of its block,
as it does in the note), `callout-fold` and `formatting`.

A block the editor does not model is rewritten in place, then read again. If
the rewrite has other blocks than the original (an HTML block become a
paragraph, say) or still goes somewhere the page cannot follow, the block is
shared as its words alone — every mark escaped, no link in it — and listed
under `formatting` by its first line. An id inside such a block stays as text,
as the editor reads it there; only one on the line after it is an id. It writes nothing, and DFAI
publishes nothing: Claude's Atlassian connector creates the page. Links and
shown blocks are read from user space only (ADR-0016), so nothing in `.atlas`
or a hidden folder reaches the page. `format` is required: one of
`confluence`, `markdown` and `standalone` (below); any other value is `invalid`.

### Exporting a note as Markdown

The same route answers a note as Markdown (#501), and writes nothing either way:

- `format=markdown` — the note as it is:
  `{ export: { path, format, title, markdown, attachments } }`. `markdown` is
  the file's text byte for byte — frontmatter, line endings and a byte-order
  mark as they are on disk; a file that is not UTF-8 is `invalid`, since JSON
  cannot carry it unchanged. `attachments` is `[{ path, as }]`: each picture
  the note's own blocks show, by its vault path, and `as` the file name a copy
  of it takes (its own name, numbered when two share one).
- `format=standalone` — Markdown that reads without the vault:
  `{ export: { path, format, title, markdown, attachments, dropped } }`. Wiki
  links are their words (the API exports one note, so no link points at
  another file), notes embedded whole are inlined and shown blocks quoted, and
  each picture is linked at `attachments/<name>`, percent-encoded
  (`attachments/Q3%20plan.png`); `attachments` lists each with that path as
  `as`, and `dropped` lists what was left out, by the kinds above.
  `frontmatter=keep` (the default) keeps the frontmatter as the file has it;
  `frontmatter=drop` leaves it off. Any other value, or `frontmatter` with
  another format, is `invalid`.

Pictures are listed by path, never sent; links, embeds and pictures are read
from user space only, so one in `.atlas` or a hidden folder is neither inlined
nor listed.

**PDF and Google Doc are app-only.** The API never writes a file — not outside
the vault, and not to a path a caller names — because any local process can
reach it (ADR-0016). A PDF is made by the app's own WebKit, from its window;
a Google Doc needs the person's consent to Google in their browser, and its
token never leaves the Keychain (ADR-0017). The person exports those from the
note's "⋯" menu or ⌘K "Export…".

### Types, and the Thumbnail property

A relation's `target` is the type it points at, and `targets` every type it
may point at — `["project", "area"]` for a task's `project`, whose type file
says `target: [project, area]`; one type is `targets: ["project"]`, and a
property that names none `[]`. `target` is `targets`' first, kept for callers that read one.
`PATCH .../properties` refuses with `invalid` a relation set to link a note of
a type it does not point at — a person in a task's `project` — naming what it
takes. Only a link to a note that is there and says its `type:` is judged: a
link to a note not written yet, or one with no type, is written as it is.

`GET /v1/types` reports each property's `kind` as the type editor has it,
`thumbnail` included (U-15). A thumbnail's value is what the app writes: empty
or `auto` means DFAI pictures the note's own page, `false` means cleared, and
a path is a picture chosen. Set it with `PATCH .../properties` like any other
value. The generated picture itself is derived and lives in DFAI's cache,
never in the vault, so no route reads or makes it; an artifact's picture is the
exception, since it is kept in its saved copy (`/v1/artifacts/{path}/thumbnail`).

### A type's views

A type owns the views whose `type:` names it, and its page shows them as tabs
(issue atlas-archive#11, ADR-0023). `GET /v1/types/{name}/views` answers those tabs as the
app draws them: `{ type, views: [{ path, title, layout, order, virtual }],
total, next }`, in tab order — views placed by their `order:` first, by that number, then the
views nobody placed, boards before tables before lists and so on, then by
name. `title` is the tab's name (the view's `title:`, else its file name), and
`order` is the view's `order:` or null when it was never placed. `{name}` is
the type's `name` exactly as `/v1/types` gives it, one percent-encoded segment;
any other is `not_found`. A view of any layout is listed, wherever it is kept —
`.atlas/views` or a note elsewhere that says `atlas: view`.

It answers a page at a time: `limit` views (1 to 500, 100 when not given) from
`offset` (0 when not given), with `total`, how many the type has, and `next`,
the `offset` of the next page or null on the last. It pages by position, as
`/v1/archive` does, not by a path cursor as `/v1/notes` does: tab order is not
path order, so a path could not say where a page ends.

A type with no views answers one tab with `virtual: true`: the default table
its page shows, named and pathed as the app would write it the moment its tabs
change ("Task table", numbered past a name already taken). The app, its tabs
and this route name it by one rule: every file already in `.atlas/views` is
taken — a view, one lifted to Today or Inbox, or a note that is no view at all
— and so is every view kept anywhere else, compared in any case and either
Unicode normalisation, as the Mac's disk compares names. It is not a file, so
`/v1/views/{path}/run` cannot run it; its rows are `/v1/query` with the type,
or `/v1/atlas-query` with `FROM <type>`. Asking writes nothing — not even the
default.

A view's `order:` counts only as a number, or as text written as a plain
decimal (`2`, `-1`, `1.5`); `"0x10"` or `"1e3"` is no order, and the view
reads among the unplaced.

`GET /v1/views` names each view's `order` too, null for a dashboard. It lists
Today and Inbox first, when the vault has them, as the sidebar lifts them —
they are views, run by their paths like any other — then the other views
alphabetically, as the Views section reads, then the dashboards.

Adding, renaming, copying, moving and deleting a type's views stay in the app;
see "Not in the API, and why" below.

### Templates

A template is what a new note starts as — its properties and its text — and it
lives in `.atlas/templates`, never among the vault's notes (issue atlas-archive#16,
ADR-0026). The API reads them; it never writes one.

`GET /v1/templates` answers every template, as the Templates page lists them:
`{ templates: [{ name, path, uses }], typesWithoutTemplate }`. Every markdown
file under the folder is one — `.md` or `.markdown`, in a subfolder too, but
not in a hidden one such as `.git` or `node_modules`. They
come sorted by name as a lookup compares it (trimmed, in any case); of two with
one name, the one nearer the top of the folder comes first.
`name` is the file name without its extension; `path` is the file. `uses` is
what makes notes from it, empty when only the New menu offers it:

| `kind`     | Made from it                      | Matched by                                   |
| ---------- | --------------------------------- | -------------------------------------------- |
| `type`     | New notes of `type` (`label`)     | the type's label, then its name, in any case |
| `daily`    | Today's note (`POST /v1/daily`)   | the name `Daily`                             |
| `capture`  | Captured tasks (`/v1/capture`)    | the name `Task`                              |
| `artifact` | Saved artifacts (`/v1/artifacts`) | the name `Artifact`                          |

`typesWithoutTemplate` names the types no template serves: a note of one made
by the add button or `/v1/quick-add` starts with only its `type:` and the
values given.

`GET /v1/templates/{name}` answers one: `{ template: { name, path, uses,
properties, body } }`, `properties` its frontmatter parsed and `body` the rest,
byte for byte — what a note made from it starts with. `{name}` is one
percent-encoded segment, matched trimmed, in any case and either Unicode
normalisation, as `POST /v1/notes { template }` matches it; of two templates
with one name it answers the one that route would use. A name no template has
is `not_found`. A template path is not a note path: `/v1/notes/{path}` refuses
`.atlas/templates/…` as it refuses all of `.atlas`.

No route that lists or follows notes hands out a template: not `/v1/notes`,
search, backlinks, tags, queries or views, even when the index still holds a
link to one. Making, renaming, editing, moving to notes and deleting templates
stay in the app; see "Not in the API, and why" below.

### Images in notes

`PUT /v1/notes/{path}/images/{name}` saves an image for a note as a paste or a
drop does (U-12): in the folder **Settings → Images** chooses when the request
arrives — `attachments/` at the root (made when missing) or beside the note —
under `{name}`, numbered past any file there in any case (`chart 2.png`), and
never over one. It takes PNG, JPEG, GIF, WebP, SVG and HEIC, up to 20 MB, as
`text` or `base64`. Its bytes must be the kind its name says (a PNG's
signature, `GIF8`, `RIFF…WEBP`, an `ftyp` HEIF brand) — the app has the webview
draw an image before saving it, and a request has nothing to draw, so a HEIC
this Mac cannot show is saved rather than refused. An SVG's root element must
be `<svg`, and one holding an HTML doctype, `<html`, `<script` or an `on…=`
handler anywhere is refused.

An image of ≤ 512 KiB is sent whole, in one request (`offset` 0, `last` left
out or `true`), and saved at once. A larger one is an **upload** (A20-02),
staged outside the notes until it is whole, so nothing in the vault is ever
appended to:

1. The first chunk: `offset` 0, `last: false`. It must start as its kind does.
   The answer is `202 { upload: { id, size } }`.
2. Each next chunk: `offset` = the `size` the last answer gave, `upload` = the
   id, `last: false` — answered `200 { upload: { id, size } }`. A chunk past
   offset 0 with no `upload` is `invalid`; an unknown id is `not_found`; the
   wrong offset is `conflict`, and nothing is written.
3. The last chunk says `last: true`. The whole image is checked and moved into
   place under a free name, answering `201 { image }`.

The name in the URL of the last chunk is the one the image is saved under. An
upload given up on is left in the cache (`.atlas-cache/uploads`), never in the
notes. The answer is

```json
{
  "image": {
    "path": "attachments/Q3 chart.png",
    "size": 48213,
    "src": "../attachments/Q3%20chart.png",
    "alt": "Q3 chart",
    "markdown": "![Q3 chart](../attachments/Q3%20chart.png)"
  }
}
```

The note is not changed: write `markdown` into it with `append` or `body`, as
`atlas_add_image` does. `![[image.png]]` embeds and resizing are not written by
the app either.

### DFAI queries

`POST /v1/atlas-query` runs a DFAI query (ADR-0019) — the text the query
builder writes — read-only, checked against the vault's types and with its
`[[links]]` resolved against its notes, exactly as the app runs it:

```json
{
  "query": "FROM task, project WHERE status != done AND tag = #q3 SORT BY due GROUP BY project THEN status",
  "limit": 200
}
```

- **Rows** are `{ columns, rows, truncated, sql }`, the columns starting
  `path`, `title`, `type`. Every value in the query is a bound parameter; `sql`
  is the statement that ran.
- **Groups.** With `GROUP BY`, `groups` lists the groups a list or table shows:
  `{ label, value, rows, groups }`, where `rows` are indexes into `rows`,
  `value` is null for the rows with none, and `groups` are the sub-groups of
  `GROUP BY a THEN b` (empty at the last level). A select's groups come in the
  type's order, a relation's are named for the note it points at, and a group
  no row is in is left out. Without `GROUP BY` there is no `groups`.
- **`this`, and `context`.** `this` in a query is the note it is about — a
  person's page asking for that person's meetings — and `context` names it,
  as a vault path:

  ```json
  {
    "query": "FROM meeting WHERE people = this AND date > @-30d AND date <= @today",
    "context": "People/Mara Quill.md"
  }
  ```

  `this` compares with a relation, with `=` or `!=`, directly or one hop
  through one (`company.owner = this`); `LINKS TO this` lists the notes whose
  body links to it, a note's link to itself left out as its backlinks leave it.
  `CONNECTED TO this` is wider: the notes a link joins to it either way round,
  in either one's body or in any property of either (a task whose `source`
  cites a meeting's turn, a meeting that lists the task) — what the app's
  linked pages ask (P30-06). After a relation of the note's own it asks about
  the notes that relation points at: `waiting_on CONNECTED TO this`.
  A query that says `this` without a `context` is `invalid`, pointing at the
  word. `context` must be a `.md` note in user space — not `.atlas` or a
  hidden folder — found however it is cased, and one the vault does not have
  is `not_found`. Its path is a bound value like any other. A bare `this`
  always means the note; to compare with the word, quote it: `'this'`.

- **Query blocks.** A note's fenced ` ```atlas-query ` block (P30-05) is note
  text, read and written with the note routes like any other. Its first line
  may say `layout: table` or `layout: list`, which is how the app draws it and
  not part of the query. To answer one as the app does, send the rest as
  `query` with that note's path as `context`.

- **Moving dates** are `@today`, `@yesterday`, `@tomorrow`, `@weekAgo`,
  `@weekAhead`, `@monthAhead`, `@startOfWeek` (this week's Monday), or a count
  from today: a sign, up to four digits, and `d`, `w`, `m` or `y` — `@-30d`,
  `@+2w`, `@+1m`, `@-1y` — reaching 1000 years at most. A range needs both
  ends: `date > @-30d` alone takes the dates to come as well. Each is the day on this machine's clock when the
  query runs; a month counts as SQLite counts one, so a month on from
  2026-01-31 is 2026-03-03.
- **Archived notes** are left out unless the query says `INCLUDE ARCHIVED`; the
  body's `includeArchived` is refused, so the answer never depends on two
  places saying different things. Notes in `.atlas` or a hidden folder are
  never listed, never read through a relation (`project.owner` shows, sorts
  and matches nothing of one), and never name a group: a relation to one
  reads as its link.
- **Limits.** `limit` is 1 to 5000; the query's own `LIMIT` wins when it is
  smaller, and with neither, 500 rows come back. `truncated` says more
  matched. A query holds 2000 conditions at most, and its text 200,000
  characters.
- **Mistakes in the text** are `invalid`, with where they are:

```json
{
  "error": {
    "code": "invalid",
    "message": "Line 2, column 7: A task has no field called stauts.",
    "at": { "line": 2, "column": 7, "start": 16, "end": 22 }
  }
}
```

`line` and `column` count from 1, columns in characters; `start` and `end` are
the offsets of the characters at fault. The index refusing the statement is
`query_failed`, with no path on this machine in its message. A query view run
through `/v1/views/{path}/run` is refused the same way, and answers up to its
own `LIMIT`, with `truncated` saying when that cut it short. A dashboard's
failed widget carries its message the same way, without paths.

### Groups, boards and "+ New"

`GET /v1/views` names each view's `groupBy` — a board's columns, a table's or
a gallery's groups — and `subGroupBy` — a board's swimlanes, a table's
sub-groups — or null for none (issue atlas-archive#6). A `subGroupBy` equal to the
`groupBy` splits nothing, so it reads as null, as the app draws it.

Running a saved view whose layout draws groups (a table, a board, a gallery)
answers its `groups` beside its rows, shaped as a DFAI query's are (below):
`{ label, value, rows, groups }`, `rows` being indexes into `rows`, and
`groups` the sub-groups — a board's swimlanes inside each column. A gallery
draws only its first level. The groups come in the order the app draws them: a
select's in the type's order (reversed when the view sorts by it descending),
a relation's named for the note, "No value" last. A board lists every column,
an empty one too — a select's every option and, for a relation, every note it
can point at (not archived notes or templates) — since an empty column is
somewhere to move a card to; inside a column, only the lanes a card is in are
listed. What a view groups by is read for its rows even when the view does
not show it as a column; `columns` is the view's own either way. A grouping by
a field that holds several values groups nothing, as in the app. A list, feed,
calendar or timeline, and a view grouping by nothing, answers no `groups`.

`POST /v1/views/{path}/move` moves a card on a board as a drag does: `note`
is its path, `group` the column and `subGroup` the lane it goes to — each a
group's `value` as a run answers it, null for "No value" — one or both. A
group must be one the board draws: a select's declared option, a note a
relation can point at, a value a card on the board already has, or null; it is
matched as the board matches its columns — trimmed, `[[atlas]]` for
`[[Projects/DFAI]]` (a relation by its first link's note name), an unticked
or missing box alike — and written as the board spells it, typed by its
property's kind (a number as a number, a checkbox as `true` or `false`). Any
other group is `invalid`, naming the board's groups, so `Done` for `done` is
refused rather than writing a column the type does not have. It is one
property write (see Writing safely: through the pane holding the note), and
the app's own rule decides whether it finishes the task: a type with a status
is finished by its done option, whether that is the board's columns or its
lanes; a type without one by its column's `done`, else its last option.
Finishing a repeating task rolls it forward to its next date once, keeping the
other group it was dropped into.

**A move that finishes the task needs `ifModified`** — the note's `modified` as
the caller read it — and is `invalid` without one. A repeating task is back in
its first status once finished, so the same move sent again would finish it,
and move its date on, a second time; with `ifModified`, the retry is refused
as `conflict` because the first move changed the note. Any other move takes
`ifModified` as optional. A group the card is already in is not written, so
`moved` is false and nothing is written when the card is in both already.
Only a board's cards move: any other layout, a lane on a board with none, a
query or SQL view, a note of another type than the view lists, a view or a
dashboard (whose `type:` names what it lists), or no `group` and no `subGroup`
is `invalid`; set a note's properties with `PATCH .../properties` instead. A
dashboard as the board is `not_found`.

`POST /v1/views/{path}/notes` adds a note as "+ New" inside a group does: of
the view's type, given `group`'s value (and `subGroup`'s, a board's lane or a
table's sub-group) typed by its property's kind — a number as a number, a
checkbox's `true` as ticked — while "No value" and the unticked group give it
nothing. It is made at the vault's root, named `name` or `New <type>`, numbered
past any note of that name rather than refused, as the app does — several added
at once each get their own number. A `name` that would not make a `.md` note
the API can read back (`Plan.markdown`) is `invalid`, as `POST /v1/notes`
refuses it; a name with no free number left after many tries, because notes
kept taking them, is `conflict`, and retrying is safe. With neither,
it is a plain note of the type. A `group` in a view that draws no groups, or a
`subGroup` in one with no second level, is `invalid`; so is a query or SQL view.

Changing a view's `groupBy` or `subGroupBy` is not a route; see Not in the API.

### Calendars

`POST /v1/views/{path}/calendar` shows a saved view's notes as its calendar
does (U-14). `range` is `month`, `week`, `3day`, `day` or `agenda` — the view's
own `calendarRange` when omitted — and `anchor` a day in it, `YYYY-MM-DD`, today
when omitted. `days` lengthens an agenda (1–366, 30 by default) and is `invalid`
for any other range. `days` in the answer lists every day shown: a week starts
on Monday, a month is its six-week grid. Each event is
`{ path, title, start, end, allDay, on }`, `start`/`end` as the note writes them
(`2026-09-22` or `2026-09-22T14:30`, wall-clock, never converted), `end` from
the view's timeline end when its timeline starts on the calendar's date, and
`on` the days of the range it is on. Notes with no readable date are counted in
`unscheduled`. The view must name a `dateKey`; a SQL view or one with no date
is `invalid`, a dashboard `not_found`.

### Quick add

`GET /v1/quick-add` lists the types the floating add button offers (U-13), as
**Settings** lists them in the vault's `.atlas/settings.md` — Task when unset —
each `{ name, label, fields }`, `fields` being the property keys the button
asks for. `POST /v1/quick-add` adds a note as the button does: from the type's
template when there is one, `values` (text by key) written as each kind stores
them, in its type's home folder (ADR-0038: a task in `Tasks/<YYYY>/<MM>/`,
a person in `People/`; a type with none at the root), numbered if the name
is taken. Any type the vault defines is
accepted, as a type's table **New** accepts it; an unknown one is `not_found`.
Which types the button offers, and where it sits, are Settings, which the API
does not change.

### Profile

`GET /v1/profile` answers who uses the vault, as **Settings → Profile** keeps
it in `.atlas/settings.md` (ADR-0024): `{ profile: { name, preferredName,
placeholder } }`, each name `null` when unset. A caller that needs the person's
name — an owner, an author, an attendee — uses `name`; when it is `null`, it
writes `placeholder` (`[Your name]`) or asks, and never guesses one from a
username, an email address or a path. The route only reads: the name is
changed in Settings, and the API never writes `.atlas`. A settings note that
cannot be read is an error, not an empty profile.

### Sources

`POST /v1/sources/{path}/refresh` refreshes a source note now, as its
**Refresh** button does (P12-06), and answers
`{ report: { ran, from, records, created, replaced, updated, missing, unkeyed, truncated, error } }`.
The source note is found as a view is: in user space or under `.atlas`, where
sources usually live (`.atlas/sources/Issues.md`), read and never written. It is
refused as `invalid` unless its `into` folder is in user space and any vault
file it reads is too — a note anyone could have written must not copy a hidden
file such as `.git/config` into notes, nor write over `.atlas`. **A source that
sends a secret, or reads a SQLite file outside the vault, runs only from
`.atlas/sources`** (A20-02), which the API cannot write: anywhere else it is
`forbidden`, nothing is fetched, and the message says to move the note into
System → sources. A public feed runs from anywhere. A SQLite file outside the
vault opens only if it was picked on this Mac.
A feed that fails is a report whose `error` says why, not an error answer. A
source already being refreshed — by its pane's timer or another request — is
`conflict`, and so is one the API refreshed less than 30 seconds ago, with
`retryAfter` saying how long is left. The refresh is bound to the vault the request arrived for: only its
secrets are sent, each filled in by the host and only to the sites it was bound
to in Settings (ADR-0017), so a source note the API pointed elsewhere is
refused by the host. `from` is the URL as the note writes it, `{{secret:name}}`
and all; no route ever carries a secret's value, and none lists secrets.

### Tags

A tag is named in the URL as one segment, its `#` optional and its `/`s
encoded: `/v1/tags/para%2Fresource/notes`. It is found however it is cased,
as the vault counts it (`IDEA` is `#idea`), and answers name it as it was
first written. A name no tag can have — no letter, or a word opening or
closing with `_` (ADR-0018) — is `invalid`; a tag no note uses is `not_found`.

`GET /v1/tags` is the tags page's tree: each tag `{ name, label, count, total,
children }`, `count` its own uses and `total` those of everything nested under
it, sorted by name or, with `?sort=frequency`, by `total`. Tags are counted in
the notes the API reads — as `/v1/notes` lists them, and as a rename writes
them — so a tag used only in `.atlas` templates or a hidden folder is not in
the tree, and is `not_found` to the other tag routes. Archived notes are left
out of the tree and of a tag's notes, as the tags page leaves them out; a
rename still rewrites them, so a note unarchived later does not keep the old
name, and a tag only archived notes use is one a rename would merge into.

`GET /v1/tags/{tag}/notes` pages the notes using the tag or one nested under it,
`{ path, title, uses }` in path order, continued with `cursor` as `/v1/notes`
is. Notes in `.atlas` are left out.

`POST /v1/tags/{tag}/rename` renames the tag, and every tag nested under it,
in the `tags` property and the body of each note, as the tags page does
(Phase 20). It answers `{ rename: { from, to, files, uses, mergesInto, notes,
skipped } }`; with `dryRun: true` that is all, and nothing is written. Otherwise
it also renames, answering `{ report: { updated, failed } }`. Each note is read
again and written against the version it read, byte for byte apart from its
tags, so a note changed in between is `failed`, not overwritten. A note open in
DFAI with unsaved typing is left alone and `failed` — the API never saves
someone's typing for them — and a pane holding a note with nothing unsaved is
reloaded. Notes in `.atlas` or a hidden folder (a template's `tags:`) are never
written: they are listed in `skipped`. A new name no tag can have, or one
nested under the tag itself (`idea` to `idea/sub`), is `invalid` with the
reason. So is a name whose last word is one letter (`plan a`): its closing
`#` reads as `C#` does, so `#plan a#` would read back as `#plan` (ADR-0018). A
note where the new name, written with its closing `#`, would run into what
follows it (`#idea_`, `#idea#x` renamed to `my tag`) keeps the old name and is
listed in `skipped` with why. **A rename into a tag already in use merges the
two** — and a tag used only as the parent of others (`#beta` when `#beta/y` is
written) is in use — and renaming back cannot part them again, so it is
`exists` unless the request says `merge: true`; `mergesInto` in the preview
names that tag. Renames in a vault run one at a time, the app's tags page's
included, and whether one merges is asked again just before it writes: two
renames into one new name, sent together, are one rename and one `exists`.

**A rename that timed out may still finish.** The API writes note by note and
does not stop when the caller gives up waiting. Preview again with `dryRun: true`
before retrying: it shows what is left to rename, and whether the new name is
now in use.

A cursor is only good for the route that handed it out: one that does not
decode to a note the API reads is `invalid`, never an empty last page.

### People: possible duplicates and merging (#464)

`GET /v1/people/duplicates` answers `{ pairs: [{ left, right, reasons }] }`:
pairs of people who may be one person, each `{ path, name }`, `left` first by
path, surest pair first. A reason is `same-email` (`email`), `same-name`
(`Tobias Fenn.md` and `People/Tobias Fenn.md`, spelt as the Terms page
compares spellings), `alias` (an alias of one is the other's name), or
`similar-email` (`left`, `right`, `local`, `sameDomain`): the same or a near
domain, and local parts that are one with their dots dropped (`same`), a
first name and a full one at a company's domain (`first-name`), or a typo
apart (`typo`). Pairs the People page was told are not one person are left
out; telling it so is the app's alone for now. A pair with a note in `.atlas`
or a hidden folder is left out.

`POST /v1/people/merge` merges the people in `merge` into `keep`, as the
People page does. Without `confirm: true` it answers `{ merge: { keep, merge,
refusal, notes, links, conflicts, aliasesAdded, emailsAdded, appended,
version } }` and writes nothing: `notes` is each note written with how many of
its links move to the kept person, the kept note last; `conflicts` the single
values the kept note keeps although a merged one says otherwise; `appended`
the heading each merged body goes under; `version` what the preview was
worked out from. With `confirm: true` and that `version` the merge is
worked out afresh and made — only while it gives the same version: a confirm
without one, or with another, is `conflict`, nothing written —, answering `{ report: { written, notWritten,
trashed, notTrashed, failures, links } }` beside it. Lists are joined, the
merged people's emails go into `other_emails` and their titles into
`aliases`, and every link to them — in a body or a property, keeping its
`|display`, `#heading` and `^block` — opens the kept person. Each file is
written once, byte for byte apart from what the merge changes, against the
version the merge read: a note changed in between is `conflict`, with nothing
written. The merged people go to the Trash only once every write has landed;
a write that fails stops the merge, and the report says what was and was not
written. Before it looks for links, preview and confirm alike save the typing
in every pane open in DFAI — any note may hold a link to a merged person just
typed — and bring the index up to the files; typing whose save is refused is
`refusal` in the preview and `conflict` with `confirm`, as is an index that
cannot catch up (`conflict` either way). A note that is not a person is
`invalid` with `confirm`. A template, a saved view or a dashboard in `.atlas`
linking to a merged person is rewritten like any note, link by link; one that
names a merged person by file rather than by a link (a query comparing a path)
refuses the merge, naming it, as does any other note of DFAI's own linking to
them. Hidden folders are never written.

### Automations

Automations (Phase 25) are read here and run in the app. The three routes
read the rules in `.atlas/automations` and their logs, as the Automations page
does, and write nothing.

`GET /v1/automations` lists every rule, by name: `{ id, name, path, enabled,
when, note, which, olderThanDays, do, set, claude, schedule, action, lastRun,
nextRun, paused }`. `when`, `which`, `olderThanDays`, `do` and `set` are the
rule as its file writes them (`set` is null for any rule but a set rule);
`schedule` and `action` say the same in the app's words. A rule whose `do` is
`claude` (P29-03) asks Claude about its notes: `claude` is `{ prompt, tools,
output, folder, data }` — the prompt note in `.atlas/prompts/`, the read tools Claude
may call, and what it writes: `proposals` or `meeting-items` (the name of a
proposal schema), which wait in the Inbox, or `note`, one new note in `folder`
(null otherwise). `data` is `weekly-review` for a step handed the weekly
review beside its notes (#40) — such a rule may have an empty `which` — and
null otherwise; its note keeps only the list items that link a note it was
given. A rule on a daily or weekly clock (`when` like `fridays at 15:00`)
that writes a note writes one each period, however often it runs (ADR-0028). `meeting-items` (P29-05) is meeting extraction: Claude
answers with action items, decisions and follow-ups, each citing one
transcript turn, and DFAI makes each a proposal — a task in the Inbox for
what the vault's owner took on, a task Waiting on whoever else did, a
Decision, or a task tagged `follow-up` — linked back to the meeting when
accepted. It may also suggest glossary terms (#19): words a turn seems to
have misheard, as a `term` proposal whose `variants` hold what was heard. DFAI
leaves out everyday words and anything the glossary already spells, and
proposes a term once, by its spelling, however many meetings suggest it;
the run's `claude.dropped` names each one left out. Accepting a term
proposal is refused when the vault has moved on since: its spelling is in
the glossary now, what it was heard as is another note's, or the new note
would take over a namesake's links.
A Claude step never edits a note. `claude` is null for every other rule.
A rule a note sets off (P29-01) has `when`
like `a meeting is created or changed`, and `note` is `{ type, on }` — `on`
holding `created`, `changed` or both; it runs once per version of each note of
that type its `which` query matches, on the Mac that runs the vault's
automations. `note` is null for every other rule. `lastRun` is the newest run,
`{ at, kind, trigger, summary }` — `kind` is `failed` when its query did not
read, and `trigger` is `note` for a run a note set off — or null. `nextRun` is
when it next runs by itself, as the app's clock counts it, a local time
`YYYY-MM-DDTHH:MM:SS`; null when it is off, runs only on opening, by hand or
when a note sets it off, or is paused until run by hand. `paused` says why the app's clock is
holding a rule back — its log could not be written, or it keeps failing — and
is null otherwise. A file that says `atlas: automation` and cannot be read as a
rule is listed apart, under `broken`, as `{ path, name, problem }`; it never
runs.

`GET /v1/automations/{id}/log` answers a rule's log, newest first, up to
`limit` entries: each `{ kind, at, heading, summary, done, left }`, with
`trigger` and `capped` on a run, `trigger` and `problem` on a run that could not
start — or whose Claude step failed — and `of` on an undo. An entry of kind
`letGo` has `count`: a rule a note sets off was held back, heard more syncs'
news than it keeps (20), and let that many go — a run by hand takes the notes
they named. `done` lists what it
did to each note — `{ kind: "archived", from, to }`, `{ kind: "set", path, key,
before, after }`, a value being `{ value }` or `{ absent: true }`, or a note a
Claude step made, `{ kind: "proposed" | "created", path }` — and `left` the
notes it matched and left alone, with why. A run or failed run of a Claude step
has `claude`, `{ model, ms }`: the model it asked and how long it took — and
`cut`, `[{ path, shown, of }]`, when a note was too long to show it whole (a
long transcript): how many characters of how many it read, which `summary` says
too. A meeting is cut between turns, never inside one. A `meeting-items` run
asks about each meeting alone and reads a long one in parts, at most ten asks a
run, under one ten-minute deadline for all of them. `claude.asks` is how many
times the model was asked (once it was; a run that never asked, for a prompt
too large to hand over say, has none, and costs nothing against the rule's
hourly cap, which counts these asks). `claude.dropped`, `[{ title, reason }]`,
names each item it left out of an answer it otherwise kept — one citing a turn
the meeting does not have, or with a kind, owner or confidence that does not
read, and the proposals past the run's most (25) — and `claude.adjusted` each
it kept with a fault put right, a due date that was no date being left off
with one step less confidence. `claude.warnings` says what to know of the run:
that the Meeting type lacks the `tasks` or `decisions` relation, so Accept
refuses the proposals. A meeting with no transcript turn is not asked about:
it is in the entry's `left`. It has `alreadyMade` when some of the proposals
it answered with were made before, by an earlier run — open, or answered since —
and so were not made again; with nothing new, its `summary` says "Nothing new to
propose (2 already made)." rather than "Claude proposed nothing." A
failed run of a Claude step cut off part-way also has `done`: the proposals it had
made, which stay. Any words the model authored in `problem` are cut to 600
characters.
A run of a rule a note sets off also has `versions`:
each `{ path, digest, wrote }` it handled, or (`wrote: true`) its own write
left; none of them sets the rule off again — and may have `went`, the paths
a note it had handled left — deleted, moved, renamed, archived, or replaced by
a new note in one sync — so a new note at one of them is new to it. A run that changed nothing is not logged. `truncated` says older
entries were left out. A
`problem`, a reason in `left`, a `summary` and `paused` never carry this
machine's paths: each is answered with `<path>` in their place, even from a log
written before the app stopped writing them.

`POST /v1/automations/{id}/dry-run` answers what the rule would do if it ran
now, found by the same use-case the app's Dry run and every run use: `{ plan:
{ do, set, claude, summary, notes, passedOver, passedOverMore, capped, cap } }`.
`notes` are the notes it would act on, at most `cap` (500, the most one run
does; 10 for a Claude step, which reads each one), and `capped` says more
matched. For a Claude step, `claude` is the prompt and tools a run would use;
Claude is not asked, and a proposal is never passed to it. A Claude step, on any
trigger, plans over the notes whose current version it has not been answered on,
as a rule a note sets off does. `passedOver` lists at most 500 of the
notes it matched and would leave alone, with why; `passedOverMore` counts the
rest. A set rule leaves out notes that already hold its values. For a rule a
note sets off, `notes` are those its query matches that it has not handled as
the index last read them — what Run now in the app would take. It
reads the notes and the index and writes nothing — no note, no log entry. A
rule that is turned off can be dry-run too.

`{id}` is the rule's `id` as the list gives it, encoded as one segment, found
whatever its case or Unicode normalization, as the disk finds its log. Two
rules whose ids differ only so share one log file, so the second (by file
name) is listed under `broken`. An id no rule has is `not_found`, repeating
at most its first 80 characters. A broken rule, named by
its name or its file's, is `invalid` with why it cannot be read — it has no
log to trust and nothing to plan. A rule whose query does not read, or that
the index cannot run, is `query_failed`, with why and without this machine's
paths. A vault switched while a route reads is `no_vault`.

### Terms

A term (P28-05, issue #11) is a name a notetaker gets wrong — a product, a
colleague, a vendor — and how it is spelt: a note of type `term`, its title
the one right spelling, `variants` the ways it is misheard, and `kind` one of
`product`, `person`, `company`, `acronym` or `other`. A Person's or a
Company's `aliases` are other spellings of their name that link an attendee to
them; they are never used to correct text (ADR-0027), so they are not in the
vocabulary.

`GET /v1/terms` answers the vocabulary the Terms page reads:

- `terms`: `{ path, canonical, variants, kind }` for each term, in the order
  of their right spellings. A `kind` that is none of the five is `null`.
- `vocabulary`: every spelling DFAI puts right, `{ form, canonical, claims }`,
  longest first, so a longer name is matched before a shorter one inside it:
  each term's title and variants, and each person's and company's name and
  variants — a name is its own right spelling, and its note's `variants` are
  corrected to it; their aliases are left out. Spellings are
  matched exactly as written, case included (`mark` and `Mark` are two); they
  are the same however they are spaced or composed. A variant with no letter
  or digit in it (`~`) is left out. `claims`
  are the notes that say so, `{ form, canonical, path, source }`, `source`
  `term`, `person` or `company`.
- `conflicts`: spellings two notes claim for two different right spellings,
  `{ form, claims }`. A conflict is not in `vocabulary`: it is not used until
  one of the notes lets it go.

Only the vault's own notes are read — not a template in `.atlas`, a note in a
hidden folder, or anything in the Archive, which is where a retired term goes.
A note counts when any item of its `type` is `term`, `person` or `company`,
as `@` and a type's page count it; one that names more than one of them is
the first it names (`type: [company, person]` is a company), its spellings
read once. The route reads the index and writes nothing, and
answers `no_vault` if another vault is opened while it reads.

**Writing a term is writing a note.** `POST /v1/notes` with `properties: {
type: "term", variants: [...], kind }` adds one (its `folder` must exist; the
Terms page files them in `Terms/`), and `PATCH /v1/notes/{path}/properties`
with `{ set: { variants: [...] } }` changes its variants — each item whole,
commas and all. The Terms page shows a variant holding a comma in double
quotes, so editing it there keeps it whole too. A Person's or a
Company's aliases are `aliases`, set the same way.

### Meetings

Meetings arrive as files n8n commits into their month's folder,
`Meetings/<YYYY>/<MM>/` (ADR-0027, ADR-0038); an older workflow's
`Inbox/Meetings/` is still read. A file in a month's folder is the import's
only when it declares `atlas_import`: a meeting made by hand there is left
alone. The
app on the Mac that runs the vault's automations imports each one, and
writes one line into it, `atlas_import_outcome`, saying how it was settled:

- `imported`: a valid meeting.
- `duplicate`: a second copy of one (same `provider` + `external_id`), also
  marked `atlas_duplicate_of` and archived.
- `error`: it breaks the import contract. It stays where it landed, marked
  `atlas_import_error` with why.

As it lets a meeting in, the import corrects the vocabulary's misheard
spellings (`GET /v1/terms`) in its Summary, Notes, Provider next steps and
Transcript (P28-06), in the same write, and records each change in the
frontmatter: `atlas_corrections`, a list of `{ from, to, count, blocks, at }`
(`blocks` the block ids changed, `at` each corrected spelling's UTF-16
offset in the body), and `atlas_corrections_digest`, a check of the body as
corrected. A meeting with nothing to correct gets neither. Read them with
`GET /v1/notes/{path}`, as any property. Undoing them is the app's alone — the
band on the meeting's page — since it rewrites a note the person is reading;
once undone, `atlas_corrections` is `undone` and the meeting is never
corrected again. A body written through `PUT .../body` after correction makes
undo refuse, as it should: the words are no longer the ones it wrote.

A file of the import's with no outcome is waiting to be imported. A
sync conflict's copy there (`… (conflict from <Mac>).md`) is never imported;
it is the person's to merge.

`GET /v1/meetings` lists them, newest first by `date` then `start`: every note
of the Meeting type, and every file marked as failing import, which may
not say it is a meeting. Each is `{ path, title, date, start, end, kind,
provider, externalId, importOutcome, importError, duplicateOf, summary }`, as its file
says; a key the file does not have is null. `importOutcome` is `imported`,
`duplicate` or `error`. A stamp cleared by hand reads `imported`, as the
import reads it. It is `pending` for an unstamped file of the import's — in
`Inbox/Meetings/`, or declaring `atlas_import` in a month's folder — waiting
for the importing Mac, and null for a meeting elsewhere the import
never handled (one filed before DFAI imported meetings, or made by hand).
`importError` says why a file failed. `duplicateOf` is the `[[link]]` to the
meeting a copy duplicates, by its path. `summary` (#186) says where the
summary Claude writes at the top of the meeting stands: `written` while the
block is the one it wrote, `edited` once the person changed it or took it
out, `pending` while the "After a meeting" rule has yet to write one, and
`none` when no rule will — it is off, the meeting was not let in, has no
transcript, is older than the 14 days the rule reaches, or was answered
already. A pending one carries `summaryPendingWhy`: the rule's last failure,
as its log says it (`Claude Code is not logged in. Fix: …`), or that the rule
has yet to run. `since` (`YYYY-MM-DD`) keeps meetings on or after
that day, and leaves out those with no `date`. Archived meetings, duplicates
among them, are left out unless `includeArchived=true`, and then carry
`archived: true`. `limit` is 1 to 500 (default 50); when `truncated` is true,
pass `next` as `offset` for the next page. A day that does not exist, or one
with a time, is `invalid`.

The route reads, and writes nothing. To fix a file that failed, write it as
any note (`PATCH .../properties` or `PUT .../body`). The importing app checks
it again when it next hears of it: once it reads, the error is taken out and
the file is stamped `imported`.

`POST /v1/meetings` (#93) takes a meeting the way n8n's workflow assembles it,
for a caller that reaches the running app rather than committing a file to the
sync repository:

```json
{
  "provider": "gemini",
  "sourceId": "19a2b3c4d5e6f701",
  "title": "Larkspur Payroll onboarding sync",
  "subject": "Notes: “Larkspur Payroll onboarding sync” Oct 6, 2026",
  "arrived": "2026-10-06T17:58:00Z",
  "attendees": [{ "name": "Mara Quill", "email": "mara.quill@example.com" }],
  "summaryMd": "## Summary\n\n…\n\n## Next steps\n\n…",
  "transcriptMd": "### 00:00:12\nMara Quill: Morning…",
  "category": "Sync",
  "timeZone": "America/Los_Angeles"
}
```

`provider`, `sourceId` and `title` are required; the rest are optional, each a
string, and null is taken as left out. An attendee is `{ name?, email?,
group? }` (`name` and `email` text or null, `group` true or false), passed to
the mapper as sent; `groupAddresses` (a list of addresses) marks more
attendees as groups, as n8n's `OPTIONS` does. Any other top-level key is
refused `invalid`, naming it: a misspelt field would otherwise write the
meeting without that content, and idempotency would keep it so. It is mapped by the
mapper n8n's Code nodes run (`packages/domain/src/meetings/mapping`, setup in
`tools/n8n/README.md`), so the start, speaker turns and attendees follow the
same rules: the day and any time come from `subject`; with no time there, the
start is `arrived` less the transcript's length, marked `start_approximate`.
An instant is read on `timeZone`'s clock, by default the zone this Mac keeps
time in. The file is checked against meeting/v1 before anything is written.

- **201** `{ meeting: { path, outcome: "written" } }`: the file is written
  into its month's folder, `Meetings/<YYYY>/<MM>/` (made if missing), at
  `<date> <title>.md`, or, when
  another meeting holds that, at `<date> <title> (<provider> <hash>).md`.
  Nothing is written over. The route writes no `atlas_import_outcome`: the
  importing Mac stamps it as it does any arrival.
- **200** `{ meeting: { path, outcome: "in-vault" } }`: the vault already
  holds this `provider` + `sourceId` (trimmed), by the import's rule — a note
  stamped `imported` anywhere, or an unstamped one that follows the contract;
  a copy marked `duplicate` or `error` does not count — or it is at one of
  its two paths. Nothing is written, so sending a meeting again, or retrying
  after a timeout, is safe.
- **400 `invalid`**: a field missing, unknown or of the wrong kind, a meeting with no
  trustworthy start (no time stated, and no transcript length to take off its
  arrival — the arrival is about when it ended, so it is never the start), a
  zone that is not one, or a file meeting/v1 would refuse; the message says
  which.
- **409 `exists`**: other meetings hold both its paths. It is not written
  under a third name.

A write is said in Activity by the route and the file, never by what it
carried; a 200 writes nothing and is not logged.

**Linking (P29-04).** As the importing app lets a meeting in, it links it,
just before the write that corrects and stamps it — so a meeting read with
`atlas_import_outcome: imported` already has its links and its corrections,
and nothing of the import's is written after:
attendees matched to People by `email` or `other_emails`, then by name or
alias (read from the Person and Company notes; the vocabulary holds no
aliases); the transcript's named speakers who are surely one person, by the
name the vocabulary corrects their label to; and
companies by an attendee's email domain (a Company's `domains`, or its `site`
when that is the site's root; the most specific declared domain wins, and a
public mail provider or shared host such as `youtube.com` claims no one). A
company named only by a domain's name, which declares no domain itself, is
proposed, never written. Sure matches are added to the meeting's
`people` and `companies`; nothing there is replaced. The rest waits in the
Inbox as proposals (see Proposals): an unknown attendee as a `person`, an
attendee two people could be — or one person of that name whose address is not
the one on file — as a `link` to each, a company guessed from a domain's name as
a `link` on `companies`, and the likeliest open project as a `link` on
`project`. A group address is never proposed, nor the vault's owner (by their
profile's name in any common spelling, or their own Person note's addresses). The
links are read as any note's are: `GET /v1/notes/{path}` gives a meeting's
`people`, `companies` and `project`, and `GET /v1/notes/{path}/backlinks` on a
person or company lists the meetings linking them. There is no route that
links a meeting; see "Not in the API".

### Proposals

What Claude or an automation proposes waits as a note of the built-in
`proposal` type in `Inbox/Proposals/` (P29-02, ADR-0028), and these routes
answer it as the Inbox page's Proposals section does, through the same use-cases.

`GET /v1/proposals` lists the open ones, newest first: `{ path, kind,
headline, confidence, source, madeBy, reason, payload, modified }`. `reason` is
why it was proposed, as the proposal's body says it (empty when it says
nothing): for an item taken from a meeting, whose it is and what to check
before accepting. `kind` is one of
`task`, `decision`, `follow-up`, `person`, `link`, `term`, `project`;
`payload` is what Accept writes, as the note holds it; `source` is the block it
cites (`[[2026-10-01 Standup#^t0003]]`), or null when it cites none. A note
proposal's payload may carry `link_from: { note, property }`: accepting makes
the note and adds a link to it to that relation of that note — a person
proposed from a meeting joins its `people`. A link proposal's `digest` is
optional: with one, the note must still hold exactly what it held when the
proposal was made; without one (what meeting linking writes), only the
relation is judged — the link is added to a list or fills an empty single
link, and never replaces one. A proposal made by a step — meeting linking, or
a rule's Claude step, through the one writer — carries
`proposal_id`, so the step proposes nothing twice, even once it was answered; a
person proposed from a meeting is known by their address alone, so rejecting
them once covers every later meeting. A payload that joins a meeting's relation
(`link_from`, or a link's own `note`) may carry `meeting: { provider,
external_id }`: a meeting is filed out of the Inbox, so accepting finds it by
that id and writes only to a note that holds that very meeting — never to the
Archive, nor to another meeting that landed at the old path, nor to whatever a
hand-edited `source` names. A rule's Claude step never writes `link_from` from
its answer: an answer that names one is refused whole. An output made for
meetings may add it itself, to a relation it fixes in code and for the meeting
the proposal cites, named by the id DFAI read from that meeting's file. One
answered but still there — the Archive refused it — is listed under `stranded`
as `{ path, headline, state }`. A note there that says it is a proposal and
cannot be read is listed under `unreadable` with why; a note there of another
type is not a proposal and is left out.

`POST /v1/proposals/{path}/accept` writes what the proposal says — a note of
its kind's type in user space, made new and never over another (a task,
follow-up or decision with `source` set to the block it cites), or one link
added to a relation of an existing note through the byte-preserving
frontmatter write — then marks it `state: accepted` and `answered_via: api`
(the app's own buttons write `app`), and moves it into the Archive. `{ accepted: { proposal, headline, archivedAt, archiveProblem,
wrote } }` names each note it `created` or `edited`. A proposal that could not
be archived is accepted all the same, with `archivedAt: null` and why.
`POST /v1/proposals/{path}/reject` writes nothing it proposed, marks it
`state: rejected` and `answered_via: api`, and archives it: `{ rejected: { proposal, archivedAt,
archiveProblem } }`.

What an accept writes is held to the task rules, as every write is: a task
Waiting with nobody to wait on is written as proposed (#202); one made
already finished gets today's `completed`, or,
when it repeats, rolls on to its next date as ticking it done would.

A task, follow-up or decision never takes the place of a note of its name: where
the name is taken it is made as "Send the notes 2", and that note is the one
linked into the meeting. Only a person already there is linked in place of
making them. A task Waiting on a person whose note has since been renamed or
deleted is a `conflict` (`waiting_on` links a note that is not there; edit it to
the right person, or to their name as text), with nothing written.

A path outside `Inbox/Proposals` is `invalid`, and one with no note
`not_found`. A proposal with typing unsaved in DFAI is `unsaved_in_app`: the
API never saves someone's typing. Everything else that stops an answer is
`conflict`, with the reason the page would show — the proposal was already
accepted or rejected; a note is already where a term or a project would go, or
(a person) is not a person; a
meeting named by its id is in the Archive, is several notes, or is now another
meeting at that path; a link's note, or a `link_from` note, changed since a
proposal with a digest was made, is gone, has no such relation, already holds
another link in a single relation, or has unsaved typing (found however the
proposal cases its path); the payload's folder is not user space — `.atlas`, a hidden
folder, one the vault never shows such as `node_modules`, the Archive or
`Inbox/Proposals`. A title too long for a file name is cut to fit. Two accepts of one proposal
make one write: the second is a `conflict`.

A `dashboard` or `view` proposal — made by `make-dashboard` above — is
accepted only in the app: accepting one here is `403 forbidden`, with nothing
written, since it writes into `.atlas`. Rejecting one is as for any proposal.

Editing a payload before accepting it, and undoing an accept, stay in the
app — see below.

### Not in the API, and why

- **Linking a meeting.** It runs once, by itself, as the importing app lets a
  meeting in (P29-04), and the "after a meeting" pipeline (#19) will run it as
  a step. Its sure links are an ordinary property write
  (`PATCH .../properties`), and what it is unsure of is proposals, which the
  Proposals routes answer.

- **Undoing a promoted line.** The app's one Undo puts the line back and
  sends the task to the Trash; taking a note away is a delete, which v1 has
  none of (ADR-0016). Put a line back with `PUT .../body`; the task stays.

- **Secrets.** Neither values nor names: ADR-0017 keeps them in the host and
  Settings; a source names one, and the host decides where it may go.
- **Types, views, dashboards, SQL queries and settings as definitions.** They
  live in `.atlas/`, which the API reads (`/v1/types`, `/v1/views`, running a
  view) but never writes: a caller that could would change what every type,
  view and template means (see Paths). The type editor, saved-view editing
  (P17-02..04) — its grouping (`groupBy`, `subGroupBy`) included — dashboard
  editing, Settings → Images and the add button's list stay in the app; a
  view's grouping is read with `/v1/views`. Tick-to-done and property edits
  are ordinary property writes, which the API has; a board drag is
  `/v1/views/{path}/move`, which writes the card, never the view. A new
  dashboard or view can be _proposed_ (`/v1/assistant/make-dashboard`, P32-05);
  only the app's Accept writes it.
- **Adding, renaming, copying, moving and deleting a type's views** (issue
  atlas-archive#11). Each writes a view in `.atlas/views` — a new file, its `title:`, a
  byte-for-byte copy, its `order:`, or the file to the Trash — and the first
  change to a type with no views writes its default table too. The API reads
  the tabs (`/v1/types/{name}/views`) but never writes `.atlas` (ADR-0016's
  addendum for issue atlas-archive#11 says why, and what an exception would take).
- **Making, renaming, editing, deleting and moving templates to notes**
  (issue atlas-archive#16). A template is a file in `.atlas/templates`, and its name is
  what ties it to the notes made from it: a caller that could write one could
  change what every new Person, today's note or every captured task starts
  as, and a rename or a delete silently stops a type using it. The API reads
  them (`/v1/templates`, `/v1/templates/{name}`) and makes notes from them
  (`POST /v1/notes { template }`), but never writes `.atlas` — ADR-0016's
  addendum for issue atlas-archive#16 says why, and what an exception would take.
- **Saving a DFAI query as a view.** `/v1/atlas-query` runs any query, but
  a query view is a note in `.atlas/views`, and the API never writes `.atlas`
  (ADR-0016): a caller that could save one could also rewrite the views James
  keeps in his sidebar and on his dashboards. Saving, renaming and editing a
  query view stays in the query builder; its saved text can be read with
  `/v1/views` and `/v1/notes/{path}`, and run with `/v1/views/{path}/run`.
- **Running, undoing, and making or editing an automation.** A rule and its
  log are notes in `.atlas/automations`, which the API never writes
  (ADR-0016): a caller that could make or edit one could set a rule that
  archives or rewrites the vault on a schedule, long after the call. A run —
  and an undo — moves or rewrites up to 500 notes at once, and the app runs
  them one at a time, with a log entry for each and its undo ready; a run from
  outside would do all that with no one watching the page it reports to. So
  running a rule now, undoing its last run, turning one on or off, and making,
  editing or deleting one stay on the Automations page. The API reads them —
  the list, each log, and a dry run that writes nothing — and a note a rule
  would archive can still be archived with `POST /v1/archive`.
- **Move, rename, delete, and making folders.** ADR-0016: every v1 write is
  additive or guarded. (Renaming a _tag_ is a guarded write to notes' text,
  not a rename of a file; see Tags.) The moves the API makes are archiving
  and unarchiving, and processing the Inbox (ADR-0016's amendments): in user
  space only, never over anything, to a place fixed by the note's own path —
  and, for the Inbox, by the project it is filed under — at most 100 notes,
  and never saving typing — see the Archive and the Inbox above.
  Moving or deleting notes, views and dashboards (P17-01)
  stays in the app; `POST /v1/notes` needs its folder to exist, so a mistyped
  folder never scatters notes.
- **Importing a meeting.** The import runs in the app, on what the index
  hears (ADR-0027): it is not a call, so a file is never imported twice or
  marked by two writers at once. A file is imported by writing it into its
  month's folder — which `POST /v1/meetings` does — and fixed by writing
  it; `GET /v1/meetings` reads the outcome.
- **Setting a vault's types up for PARA** (P30-01). Opening a vault that has a
  Project type writes the Area and Resource types it lacks; anything more —
  PARA's types for a vault without one, or `project` added to its own Task and
  Meeting types — the Inbox offers, and writes only when James accepts. Each is
  a write into `.atlas/types`, which the API never makes (see Paths): the
  types it would write can be read with `/v1/types` once they are there.
- **Editing a proposal before accepting it, and undoing an accept.** Edit is
  the person changing what a proposal would write, which is the point of
  asking them; a caller that wants something else written writes it with the
  note routes. Undo takes back what an accept made only if nothing changed it
  since, and is offered once, on the page that reported the accept — the app
  holds what it needs, not the vault. Making a proposal is P29-03's Claude
  step, in the app, not a route.
- **Writing the Block type** (P31-01). The app writes it once a vault's tasks
  follow GTD; it is a write into `.atlas/types`, which the API never makes.
  Blocks themselves are notes, made and changed through the notes routes.
- **Google Calendar, beyond whether it is connected.** `/v1/status` answers
  `googleCalendar: { connected }` for the open vault (null with no vault
  open) and nothing more: not the client, the scopes, or a token, and no
  route makes a calendar call. Connecting signs in in the browser, which a
  request cannot do, and the tokens never leave the host (ADR-0030).
  Connecting, disconnecting and choosing the calendar blocks go to stay in
  Settings → Google Calendar.
- **Picking a SQLite file for a source.** A file outside the vault opens only
  once it was picked on this Mac in the system dialog; a request cannot pick one.
- **Page pictures.** Derived, in the cache; see Types above.

Filter operators: `is`, `isNot`, `contains`, `startsWith`, `greaterThan`,
`lessThan`, `isEmpty`, `isNotEmpty`.

## MCP

`apps/mcp` exposes each route as a tool (`atlas_search`, `atlas_read_note`,
`atlas_create_note`, …; `atlas_save_artifact` covers the three artifact routes,
chunking what does not fit, and `atlas_add_image` sends an image whole or as
an upload, then appends it to the note; a `file` it reads only from the image
folders its README names) over stdio and reads the connection file itself.
`atlas_calendar`, `atlas_quick_add_types`, `atlas_quick_add` and
`atlas_refresh_source` are the calendar, quick-add and source routes;
`atlas_profile` is the profile route, read-only;
`atlas_export_note` is the export route, read-only: `format` is `confluence` (the default), `markdown` or `standalone`, with `frontmatter` for `standalone`;
`atlas_list_templates` and `atlas_read_template` are the template routes, read-only;
`atlas_tags`, `atlas_tagged_notes` and `atlas_rename_tag` are the tag routes;
`atlas_terms` is the terms route, read-only;
`atlas_rename_tag` previews unless called with `dryRun: false`.
`atlas_find_duplicate_people` and `atlas_merge_people` are the people routes;
`atlas_merge_people` previews unless called with `confirm: true` and the preview's `version`.
`atlas_archive`, `atlas_unarchive` and `atlas_archived` are the Archive's;
`atlas_process_inbox_item` is the Inbox's Process, filing one note under a
project or an area; `atlas_clarify_inbox_item` is `/v1/inbox/clarify`; `atlas_schedule_task` makes a block for a task
(`/v1/tasks/schedule`); and
`atlas_search`, `atlas_run_view` and `atlas_query` take `includeArchived`, and
`atlas_query` takes `schedule` for a query of tasks.
`atlas_run_query` runs a DFAI query (`/v1/atlas-query`), with `context`
for the note `this` names; it has no `includeArchived`, since the query's own
`INCLUDE ARCHIVED` says it.
`atlas_automations`, `atlas_automation_log` and `atlas_automation_dry_run` are
the automations routes, all read-only. `atlas_meetings` is the meetings route,
read-only. `atlas_brief`, `atlas_open_loops` and `atlas_meeting_quotes` are
the assistant routes, read-only, and the chat and a rule's Claude step reach
them by the same names. `POST /v1/meetings` has no tool: it takes a provider's raw meeting
and email for a program like n8n, and a model asked to record a meeting can
already write a note with `atlas_create_note`. `atlas_proposals`, `atlas_accept_proposal` and `atlas_reject_proposal`
are the proposal routes. `atlas_move_card` and `atlas_add_to_view`
are the board move and the "+ New" in a group; `atlas_move_card` is not marked
idempotent, since a move into done sent twice would finish a repeating task
twice (it needs `ifModified`, above). A
path or name of only `.` or `..` is refused before any request, since the URL
would resolve it onto another route (a tag's is sent with its `#`). Its
README lists every tool and has the snippet for Claude Code and Claude Desktop.
